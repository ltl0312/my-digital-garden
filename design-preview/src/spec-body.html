01现状诊断

先看清楚现在是什么，再谈改什么。以下结论全部来自代码通读与线上真实页面测量，不是主观印象。

1.1 代码逻辑梳理

前端共 19 个文件、约 1750 行，是一套相当克制、职责清晰的实现。理解它之后可以确认：本次改版完全可以在表现层完成，不需要触碰任何数据流与接口。

1.2 问题清单

按影响程度分三级。P0 = 阻断性、P1 = 显著影响效率或观感、P2 = 打磨项。

级别问题证据改版对策
P0 移动端完全不可用 390px 视口下测得侧栏固定占宽 320px，主内容区只剩 66px（标题栏内可用宽度 34px），正文呈逐字换行；顶栏品牌区的 "Non-linear Knowledge Sanctuary" 竖排成 4 行。 新增单列外壳：图标栏隐藏 → 侧栏改为抽屉式（overlay + 遮罩），顶栏精简为「汉堡 + 标题 + 搜索 + 用户」
P0 字号系统性偏小 线上文本节点字号分布：9px ×40、10px ×26、11px ×76、12px ×47 —— 142 / 221 = 64% 的文本小于 12px。中文在小字号 + 无衬线细体下可读性很差。 建立 11–46px 的字号阶梯，正文提到 15px / 行高 1.75，界面最小字号锁定 12px；正文与摘要改用 1.75–1.85 行高
P0 标签体系失效 55 个标签，而侧栏只渲染 tags.slice(0, 20) —— 35 个标签在界面上永远不可见；同时「按标签筛选」只有一个纯文本输入框，用户必须精确记住标签名才能命中。 标签按命名空间前缀分组（status/ type/ 及领域前缀），组内可完整展开；列表页活动筛选以可移除芯片呈现
P1 导航价值缺失：一棵"退化"的文件树 真实 vault 是单根结构：KnowledgeBase 下 11 个一级目录、最深 6 段 slug。侧栏把唯一根目录当作根渲染，白占一级缩进，中文目录名被截断成 03_K…。 单根目录自动提升为根；新增「领域」面板（前端/后端/数据库/运维/计算机基础/软件工程/跨学科 7 个族，带占比条）作为主迷航入口
P1 列表缺少可辨识信息 最近 48 篇里 47 篇 summary 为 null、47 篇 readingTime 为 0 → 列表大面积出现「暂无摘要」，且没有路径信息。而存在标题重名（如多篇「环境配置与项目初始化」），用户无法区分。 卡片改为「行」结构：补上 完整路径（已有数据）、领域徽章、阅读时长；无摘要时以路径替代占位文案，不再输出「暂无摘要」
P1 知识图谱大面积留白、标签不可读 287 节点 / 278 边，其中 9 篇孤立笔记（度为 0）。原生力导向把孤立节点甩到画布边缘，同时全局只有一个颜色（287 篇 maturity 全为 SEEDLING），整图呈单色紫。 孤立节点改到外围轨道等距排布（虚线描边，自成一类）；默认按「领域」着色（7 色族）；标签加描边底衬避免互相压叠；搜索定位、图例、统计、设置全部改为浮层控件
P1 原生弹窗打断体验 新建笔记用 prompt()、错误用 alert()、删除用 confirm()（[...slug].vue、default.vue、FileTree.vue、admin.vue 共 7 处）。浏览器原生对话框会中断任务、无法承载结构（目录选择、字段校验、危险说明）。 统一为应用内对话框 + Toast：新建笔记（标题 + 目录 + 校验）、删除确认（含文件路径与不可恢复说明）、操作结果提示
P1 关键操作缺少确认成本与反馈 管理后台密钥直接明文铺在表格里；「禁用 / 删除」是两个 11px 文字链，且禁用/启用状态只有文字差异，没有开关控件；生成后的密钥只以一行普通文字展示，无法复制。 密钥默认打码 + 显示/复制按钮；状态改为 switch 控件；生成结果用强调面板展示并支持一键复制；删除走确认对话框
P1 顶栏信息重复、动作语义含混 「Notes / Graph / Admin」胶囊与侧栏、首页入口三处重复；退出登录是一个 11px 灰字；主题按钮在暗色下显示太阳图标（语义指向不明确）。 主导航收敛为左侧图标栏（唯一入口，带当前态指示）；顶栏只保留「搜索 / 新建 / 主题 / 侧栏 / 用户」；用户菜单承载身份、主题、密钥管理、退出
P2 登录页信息量不足 只有一个输入框和一个按钮，右侧大面积空白；没有说明这是什么、密钥从哪来、有效期多久（这些信息其实全都存在）。 左右分栏：左侧品牌与能力说明（数据取自真实功能），右侧表单含密码可见性切换、错误态、免责说明
P2 长路径导航断裂 阅读器面包屑只取 slug 的第一段（Garden Vault / KnowledgeBase），而实际层级最深 6 段，用户丢失位置感。 面包屑渲染完整路径（可换行、末尾高亮），右侧目录栏附带属性面板（成熟度/领域/时长/反链/最近更新）
P2 命令面板只能"回车进第一个" CommandPalette.vue 支持防抖与请求竞态控制（做得很好），但结果列表没有键盘上下移动，也没有可点击的父级分组，Enter 只能打开第一条。 保留防抖与竞态逻辑，补齐 ↑↓ 选择、Enter 打开、结果按「笔记 / 标签 / 页面」分组、关键词高亮、底部快捷键提示
P2 无障碍与状态反馈缺口 大量扁平 <div> 承担按钮职责（文件树行、标签云、TOC 项）；无 :focus-visible 规范；主题切换后无过渡统一策略之外的状态提示；无 prefers-reduced-motion 处理。 全部交互元素改为语义化 <button>/<a> 并补 aria-*；统一 focus ring；补 reduced-motion 分支
内容层面的两点发现（建议在数据管道侧另行处理，界面层已做兜底）：
① 摘要字段几乎为空，且唯一有值的那条摘要夹带了原始 Markdown（## 信息来源 - **官方文档**…），不适合直接展示 —— 界面层改为优先展示真实存在的路径信息。
② 287 篇笔记的 maturity 全为 SEEDLING，导致「按成熟度着色」「幼苗/成长/常青」三色徽章在真实数据下退化为单色；新方案因此将默认着色方式改为「按领域」，同时保留成熟度视图。

02改版目标与设计方向

三条目标，决定了下面所有取舍。

① 先能读，再好看

这是一个阅读型产品。字号、行高、对比度、阅读宽度优先于装饰。玻璃拟态从「随处可见」降级为「只用于浮层与顶栏」，内容卡片改用实色 + 细描边，减少视觉噪声。

② 让 287 篇笔记可被导航

单靠文件树无法管理近 300 篇笔记。用领域 / 类型 / 状态三个维度提供结构性入口，标签按命名空间分组展开，把"记住标签名"变成"点一下"。

③ 双端都要能用

移动端不是桌面端的缩小版。侧栏抽屉化、顶栏动作收敛、列表信息重排、图谱最小可读缩放 —— 全部单独设计，而非依赖响应式缩放。

视觉方向：暖纸 × 深墨 × 玉青

保留「花园」的品牌内核（青绿 = 生长），但把它从到处都在的装饰色收敛为唯一的交互色： 亮色采用暖纸底色（不再是纯白 + 绿色蒙版），暗色采用带蓝相的深墨（不再是纯黑 + 绿光晕）。 Latin 展示文字用已引入的 Newsreader 衬线体做点缀，中文全部走清晰无衬线并加大字号 —— 避免中文衬线在 Windows 上回退到宋体。

05页面级方案

每个页面给出：现状问题 → 改版要点 → 组件结构。所有改动都在模板与样式层。

5.1 登录页

改版要点：左右分栏。左侧承载品牌与产品能力（双向链接 / 知识图谱 / 沉浸阅读 / 密钥访问，全部取自真实功能，不是营销文案），配一个纯 SVG 的花园连线插画（与知识图谱同构）；右侧是表单，含密码可见性切换、行内错误态、有效期说明。窄屏下左侧自动隐藏、只留表单。

5.2 首页

现状问题：只有「✨ 拾光」标题 + 8 条列表；两条跳转链接被塞在区块标题右侧；未利用任何已有统计信息。

改版要点：

  • Hero：眉标（Newsreader italic）+ 主标题 + 一句话说明 + 三个动作（开始浏览 / 打开图谱 / 搜索 ⌘K），把「下一步做什么」前置。
  • 统计条：笔记总数 287 / 标签 55 / 双向链接 278 / 知识领域 7 —— 全部来自现有接口（/api/vault/tree、/api/tags、/api/notes/graph）。
  • 最近更新：从 8 条卡片改为 6 条信息密度更高的行，右侧「全部笔记 →」。
  • 右栏：快速入口（全部笔记 / 知识图谱 / 访问密钥）、常用标签（Top 12，点击即筛选）、Vault 同步状态。

5.3 全部笔记

现状问题：卡片把 4 行信息压进 11px 小字；没有路径，重名笔记无法区分；筛选只有两个裸输入框；标签行是 20 个平铺小胶囊；分页只有「上一页 / 下一页」。

改版要点：

  • 行式列表：左缘 3px 领域色条（悬停显现）→ 徽章行（成熟度 · 领域 · 阅读时长 · 日期）→ 标题 17px → 路径（等宽 12px，真实数据）→ 摘要 2 行 → 标签（最多 3 个 + N）。无摘要时用路径替代「暂无摘要」。
  • 工具栏：搜索（带清除按钮）+ 排序（最近更新 / 标题 / 阅读时长）+ 密度切换（标准 / 紧凑，前端本地状态）。
  • 活动筛选：以可逐项移除的芯片呈现，并提供「全部清除」；空结果给出原因与下一步建议。
  • 分页：窗口化页码（1 … 3 4 5 … 48）替代仅有前后两键。

5.4 笔记详情

现状问题：目录（TOC）以一个大卡片横在正文之前，长文时正文被推得很低；面包屑只显示第一层；反链区块缺乏来源上下文。

改版要点：

07交互与可访问性规范

右键与长按

  • 结构树右键 = 该节点的操作菜单；触屏长按 500ms 等价于右键（pointerType === 'mouse' 时忽略长按，避免与拖拽冲突）。

  • ⌘K / Ctrl K 打开命令面板；ESC 关闭任意浮层
  • 命令面板内 ↑ ↓ 移动、Enter 打开
  • ⌘\ 收起 / 展开侧栏
  • 所有交互元素可达、可聚焦，顺序符合视觉顺序

  • 侧栏行、标签、目录项改用 <button>/<a>，补 aria-current / aria-pressed / role="switch"
  • 对话框 role="dialog" aria-modal="true"，标题用 aria-labelledby 关联
  • Toast 容器 aria-live="polite"

  • 操作结果统一 Toast（成功 / 警告 / 失败三态）

四条设计决定

  • 只读身份下，写操作"全部可见 + 逐项置灰"，而不是整项消失。第一版实现里「重命名 / 删除」整项不渲染、而「新建」却置灰 —— 同一个菜单两套处理方式，看着像坏了。统一之后，权限边界是自解释的：能点的都能点，不能点的都写明了为什么。
  • 「不能点」的原因写在菜单项右侧（并同时进 title），不需要 hover 才知道，也不用点一下等报错。
  • 结构保护是所有人的红线：vault 一级目录（00_Inbox / 03_Knowledge …）任何角色都不能重命名或删除 —— 它们是知识库骨架，误删代价远大于收益。要调整结构，就在其中增删内容。
  • 「非空文件夹」是介于两者之间的一档：普通管理员能管理日常内容（删单篇、删空目录），但整目录端掉需要初始管理员——批量删除的破坏面比单篇大一到两个数量级。
两处需要你确认的推断（需求未明说）：
① 「非空文件夹仅初始管理员可删」：需求只说了禁用/删除的用户层级，没提文件树。这里按"破坏面"分档：普通管理员管内容，初始管理员管结构。
② 结构目录全员不可改：包括初始管理员。若你希望初始管理员可以重命名一级目录，把 permRename / permDelete 里的结构保护判断加上 && state.role !== 'root' 即可。

③ 任何人都不能禁用 / 删除自己正在使用的密钥，避免把自己锁在门外。

8.3 同一页面的三种形态

管理后台不是「按角色隐藏几个按钮」，而是同一路由的三种不同呈现：初始管理员看到全部、普通管理员看到收窄后的子集、普通用户看到的是一张无权限页。

两处刻意的设计决定

  • 把"看不到什么"讲出来，而不是静默隐藏。普通管理员的列表上方有一段说明：只能看到自己与普通用户，初始管理员与其他管理员的密钥不在可见范围内（服务端同样会拒绝返回）。否则用户会以为密钥被误删了。
  • 不可操作的行把原因写在 hover 里。初始管理员行的开关被替换为 🔒 内置身份；普通管理员看自己那行时，禁用 / 删除按钮置灰并提示「不能变更自己的密钥状态」。比"点了没反应"清晰得多。

8.4 每个角色都能看到自己的权限边界

新增「我的密钥」页（所有角色可见），用一张身份卡 + 一份权限清单把当前角色能做什么、不能做什么讲清楚。普通用户因此有地方查看自己的密钥，而不是必须去找管理员。

8.5 越权兜底：界面隐藏 ≠ 权限生效

原型里做了两层：界面层按角色渲染，运行时再拦一道。测试脚本刻意绕过 disabled 直接触发点击，验证运行时判断仍然生效：

越权尝试界面层运行时拦截
普通管理员禁用自己开关置灰越权操作：不能变更自己的密钥状态
删除初始管理员按钮置灰越权操作：初始管理员不可被删除
普通用户进入管理后台入口不渲染渲染为无权限页（真实实现返回 403）
普通用户编辑笔记不出现编辑 / 删除按钮当前身份为普通用户，没有编辑权限
必须落到服务端的部分：界面层的可见性只是第一道门。真实实现里 ① 管理类接口要同时校验发起者角色与目标对象角色（只看路径权限是不够的）； ② 可见范围应下沉到查询层（where 条件），而不是取全量再在前端过滤； ③ 初始管理员的保护位要在服务端生效，任何 disable / delete 请求针对它都返回 403。

8.6 新建文件夹

入口放在「结构」面板的段控行右侧（仅在结构面板 + 管理员身份时出现），与笔记的创建动作分开，避免在标签 / 领域面板里出现语义不符的按钮。

  • 父目录首项是 vault 根目录：否则新建一级目录（如 07_Archive）时会被迫塞进第一个已有文件夹。
  • 行内校验：空名称、非法字符（\ / : * ? " < > |）、同层重名、超长名称，都在对话框内就地提示，不用弹窗。
  • 创建后在树中定位：自动切回「结构」面板、展开父目录与新文件夹。
  • 权限：普通用户既不出现入口，直接触发也会被运行时拦截。

09批量导入（单个文件 / 整个文件夹）

入口收进顶栏「新建」下拉（新建笔记 / 新建文件夹 / 导入笔记），不新占一级导航。整条链路只有一件事：在用户动手之前，就把「能不能导」说清楚。

9.1 四步流程

对话框按「来源 → 目标 → 校验 → 结果」四段推进，前三段同屏可见（不是分页向导），用户可以来回改任意一项并立刻看到重新校验的结果。

步骤内容关键点
① 选择来源拖拽区 + 「选择文件」/「选择文件夹」两个按钮；支持 .md / .markdown / .txt文件夹走 webkitdirectory，用 webkitRelativePath 还原来源层级；拖拽目录用 FileSystemEntry 递归读取
② 目标位置父目录下拉（含 /（vault 顶层））+ 可选新建子文件夹 + 是否保留来源层级路径预览实时显示 content/vault/… 的完整落点，不用脑补
③ 大小校验阻断横幅 → 两条上限计量条 → 逐文件清单（体积 / 落点 / 判定）结论徽章放在步骤标题上（校验通过 / 已阻止），不滚动就能看到判定
④ 导入结果成功篇数 / 跳过个数 / 写入体积 / 目标目录 + 跳过原因清单清单冻结在导入那一刻的判定，不会因为文件已落盘而全翻成「已存在」

9.2 两条硬限制与校验时机

规则阈值前端（选择后立即）服务端（真实字节数复核）
单个文件大小≤ 5 MB读 File.size 直接判定，超限即置为阻断读完整流后再判一次（Content-Length 与 file.size 都不可信）
单个文件夹总大小≤ 100 MB对「待导入文件」求和，超限即置为阻断按导入会话（jobId）累计已写字节，越线立即中止并回滚
单次文件数≤ 500同样的预检与提示预检接口限额
文件类型.md / .markdown / .txt不支持的类型标为「跳过」，不阻断整体白名单校验，非白名单拒绝写入
文件名唯一性同一目录内不可重名与目标目录已有文件重名、或本批选择内部重名 → 阻断整体写入前 fs.access 复查；重命名 / 新建 / 粘贴共用同一条规则
三条已确认的口径（本轮定稿）：
① 1 MB = 1024 × 1024 字节 —— 与系统「文件属性」一致，不是 106。按 106 算的话 5 MB 会放宽到 5.24 MB，边界行为会与验收标准对不上。
② 100 MB 只统计「待导入文件」 —— 被类型过滤掉的文件（如 .png）根本不会写入 vault，因此不计入总量；界面上明确标注「已跳过 N 个不计入」，不做静默扣减。
③ 文件名不可重复 —— 同一目录下不允许存在同名笔记。没有"跳过 / 自动重命名 / 覆盖"三选一：重名一律阻断整批导入，并给出解法（在结构树里右键重命名旧笔记，或换一个子文件夹）。这条规则同时是新建笔记、重命名、粘贴的规则，全项目只有一处实现（nameProblem()）。

9.3 阻断提示：把「为什么挡住」说完整

被挡住时最糟的处理是「按钮变灰、不给原因」。这里的提示包含四件事：哪条规则、超了多少、卡在哪个文件上、怎么解决。

触发条件提示文案（实际渲染）
单个文件超限已阻止导入：单个文件不得超过 5 MB　→　single-6.2mb.md　6.20 MB · 超出 1.20 MB
文件夹总量超限已阻止导入：单个文件夹总大小不得超过 100 MB　→　待导入合计 104.0 MB　超出 4.00 MB
文件数超限已阻止导入：单次导入文件数不得超过 500 个　→　待导入 620 个文件　超出 120 个
文件名非法已阻止导入：文件名包含非法字符，无法写入 vault　→　含 \ / : * ? " < > | 等字符
  • 三种状态用三套语义色，不靠文字辨别。计量条：正常（青）/ 预警 >80%（琥珀）/ 超限（红并整块底色变红）。文件行：可导入 / 跳过（灰）/ 超限（红底红字）。
  • 超限的文件单独列出来，不合并在总数里。「可导入 0 · 跳过 0 · 超限 1」比「1 个文件有问题」可行动得多。
  • 能救的与不能救的分开说。单文件超限只能先在本地拆分（「无法通过分批绕过」）；总量超限可以分批导入 —— 提示必须区分，否则用户会白试。

9.4 通过态与结果态

结果面板里保留一句「服务端会以真实字节数复核一次」—— 既是给用户的说明，也是给实现的提醒。

9.5 目标路径、目录结构与文件名唯一性

  • 删掉「保留来源层级」就全部拍平到同一目录，列表里每一行的落点会实时跟着变 —— 用户在按下导入之前就能确认文件会落在哪里。
  • 父目录下拉首项是 vault 顶层，而不是第一个已有文件夹（否则新建一级目录时会被迫塞进别人家里）。
  • 重名不是"策略"，是规则。早先版本提供了「跳过 / 自动重命名 / 覆盖」三种策略，看着灵活，实际让规则变含糊：同一个操作在不同设置下结果完全不同，用户没法预期。本轮收敛为唯一规则「同一目录不可重名」——重名就阻断整批，并把解法写清楚。这条规则同时约束新建笔记、树内重命名与粘贴，四处共用同一个校验函数。
其它类型过滤与响应式：混选时 .png 被标为「类型不支持（.png）」而整体照常通过（可导入 2 · 跳过 1）；390px 视口下对话框转为单列、动作按钮拉通、清单省略体积列保留名称与判定。

10成熟度标签的定义与治理

「几乎全部笔记都是幼苗」不是作者打标的问题，而是这个字段从来没有被使用过。本章给出失效诊断、判定标准、边界划分与可执行的批量修正工具。

10.1 失效诊断：三个叠加的根因

对 content/vault 全量 289 个 .md 的扫描结论：

事实数据含义
maturity 字段填写数0 / 289不是"都标成幼苗"，是"从没人标过"
status/* 标签维护数179 / 289（进行中 144 · 已完成 27 · 待处理 8）同一批作者在认真维护另一套状态体系
创建时间分布2026-06 一批生成 255 篇（占 88%），无 14 天内新建整库是一次性批量生成的，从未经历真实"生长"
线上呈现列表徽章直接渲染英文枚举 SEEDLING即使有区分，界面也没有可读的成熟度表达

机制上，两处默认值把整个维度填平了：prisma/schema.prisma 的 @default(SEEDLING)，与 server/utils/markdown.ts 的 frontmatter.maturity || 'SEEDLING'（非法值同样回退 SEEDLING）。笔记模板（05_Templates/原子笔记.md）的 frontmatter 里根本没有 maturity 行——生成工具自然不会写它。

10.2 语义定位：三个正交维度，不可互替

失效的深层原因是语义混叠：库里同时存在三套"看起来都像状态"的体系，但它们回答的是三个不同的问题。

维度回答谁的问题示例谁维护
maturity（成熟度）读者：「这篇我能依赖到什么程度？」幼苗 / 成长 / 常青应可自动判定 + 人工覆盖
status/*（写作进度）作者：「我写到哪了？还有待办吗？」待处理 / 进行中 / 已完成作者手工（已在维护）
type/*（形态）「这篇是什么形态的内容？」笔记 / 教程 / MOC作者手工（已在维护）
交叉验证「不可互替」：27 篇标了 status/已完成 的笔记，按 10.3 的标准重评后没有一篇达到常青（全部为成长）。「我认为写完了」≠「读者可以依赖」。反过来，status/进行中 的 144 篇里有 18 篇已满足常青标准——内容已稳定，只是作者还留着状态标签。两个维度各自有效，合并任何一方都会丢信息。

10.3 判定标准：模板契约完成度（可自动化）

这套笔记有严格的模板契约：五区块（知识体系定位 / 概述 / 设计初衷 / 实现 / 关联上下文）+ 关联上下文的 4~5 个维度（横向对比 / 实际应用 / 前置知识 / 进阶方向 / 易混淆概念，缺失维度用 📋 待补充 占位）。契约完成度本身就是成熟度——它是作者自己定义的、逐篇留痕的、可机器读取的标准，不需要任何主观打分。
