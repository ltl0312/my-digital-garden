# 多端测试策略与专项测试

## 📍 知识体系定位
- **所属技术栈**：软件工程 / 质量保证（QA）
- **所在层级**：L2 质量保证 → 测试类型 + 多端专项测试
- **上游依赖**：<a href="obsidian://open?file=软件项目全流程-SDLC八阶段模型">SDLC 八阶段模型</a>（第六阶段测试的宏观框架）；<a href="obsidian://open?file=多端设计规范与技术选型">多端设计规范与技术选型</a>（测试策略因技术选型而异）
- **下游延伸**：自动化测试框架（Selenium/Jest/JUnit）、CI/CD 测试流水线、性能测试工具（JMeter）
- **同级技术**：手工测试、自动化测试、混沌工程、A/B 测试

## 概述（Overview）
> 软件测试是在产品发布前系统性地发现和消除缺陷的过程。多端测试的核心挑战在于：同一个功能在不同平台（Web/App/小程序/桌面端）上运行在完全不同的运行时环境中，需要在**通用测试类型**的基础上追加**平台专项测试**。

## 设计初衷（Motivation）

### 历史演进
- **前身技术**：手工点点点测试（1990s-2000s 主流），没有自动化，回归测试靠人肉
- **为什么前身被淘汰**：手工测试无法跟上敏捷开发的快速迭代节奏；多端场景下手工测试成本指数级增长（一个功能要测 4-5 个平台）
- **本方法论的核心突破**：结合"测试金字塔"思想（单元:集成:端到端 ≈ 7:2:1）与"平台专项测试"维度，形成二维测试矩阵（测试类型 × 平台类型）
- **为什么是它活下来了**："测试左移"（Bug 越早发现成本越低）+ "自动化分层"（不能什么都自动化，也不能什么都手工）——这是工业界经过大量血泪教训收敛出的最佳实践
- **当前版本**：2025-2026 主流测试工具链：Jest/Vitest（前端单元）、JUnit 5（Java）、Playwright/Cypress（E2E）、JMeter/K6（性能）、Appium（移动端自动化）

### 设计思想
测试的核心设计哲学是**分层防御**：
1. **越快越便宜的测试越要在前面多跑**（单元测试毫秒级 → 开发时随手跑）
2. **越接近用户真实场景的测试越不可省略**（端到端测试分钟级 → 合入主干前必须跑）
3. **平台差异是真实存在的，不能靠"我觉得应该没问题"来保证质量**

> **💡 补充**：在发布前将 Bug 扼杀在摇篮中。测试不是测试工程师一个人的事——Code Review 是开发阶段的"静态测试"，产品验收是产品经理的"业务测试"，线上监控是运维的"生产测试"。

## 实现（Implementation）

### 完整实例：一个跨平台电商 App 的测试矩阵

#### 一、通用测试类型（所有平台共用）

1. **冒烟测试**：核心主流程能否跑通（用户能否完成"注册→浏览→下单→支付"全链路）
2. **功能测试**：对照 PRD 逐项验证每一条功能描述
3. **性能测试**：使用 JMeter 模拟高并发，测试服务器吞吐量和响应时间——例如："1000 并发用户同时抢购，服务器响应时间是否 ≤ 2s"
4. **安全测试**：渗透测试、SQL 注入防范、越权访问检查（如普通用户能否通过改 URL 参数访问他人订单）

> **💡 补充**：性能测试的目标不是"测出服务器能跑多快"，而是"确认系统在预期负载下正常运行"和"找到系统的性能拐点（多少并发时会崩溃）"。

#### 二、各端专项测试（平台特有风险点）

| **平台类型** | **专项测试关注点**                                               |
| ------------ | ---------------------------------------------------------------- |
| **Web**      | 浏览器兼容性测试（Chrome, Safari, Edge 各版本），首屏加载性能     |
| **App**      | 机型碎片化适配（不同分辨率、刘海屏、异形屏），弱网环境测试（2G/3G/丢包），耗电量与内存泄漏测试，不同系统版本（iOS 15/16/17/18）兼容 |
| **小程序**   | iOS 与 Android 宿主环境下的渲染差异测试（如 WXSS 动画在 iOS 流畅但 Android 卡顿），各宿主版本 API 兼容性 |
| **EXE**      | 操作系统兼容性（Win 10/11, Mac Intel/Apple Silicon），安装卸载流畅度（残留文件/注册表），离线使用能力（断网后核心功能是否正常） |

> **💡 补充**：App 的弱网测试常被忽略但杀伤力极大。中国的移动网络环境极其复杂（地铁、电梯、地下室），一个在网络良好环境下完美运行的 App 在弱网下可能崩溃、白屏或丢数据。推荐使用 Fiddler/Charles 模拟延迟和丢包。

### 关键参数/配置说明

| 测试维度 | 工具推荐 | 核心关注指标 |
|----------|---------|-------------|
| 单元测试 | Jest / JUnit 5 / Vitest | 代码覆盖率 ≥ 70%（核心逻辑 ≥ 90%） |
| E2E 测试 | Playwright / Cypress | 关键业务流程通过率 100% |
| 性能测试 | JMeter / K6 | 平均响应时间 / P99 延迟 / 吞吐量（TPS） |
| 移动专项 | Appium / 真机云测平台 | 兼容设备覆盖率 ≥ Top 50 机型 |
| 安全测试 | OWASP ZAP / Burp Suite | OWASP Top 10 漏洞清零 |
