# 软件项目全流程 — SDLC 八阶段模型

## 📍 知识体系定位
- **所属技术栈**：软件工程 / 项目管理
- **所在层级**：L0 项目管理方法论 → SDLC（软件开发生命周期）
- **上游依赖**：无（入门级通识），有软件开发基础经验者理解更深
- **下游延伸**：敏捷开发（Scrum/Sprint）、DevOps 持续交付、多端项目实战管理
- **同级技术**：瀑布模型、螺旋模型、RUP 统一过程、Scrum 敏捷框架

## 概述（Overview）
> SDLC（Software Development Life Cycle，软件开发生命周期）是一个软件项目从立项到最终落地（上线交付）所必须经历的一套严密管理框架。它定义了"做什么→怎么做→做得对不对→怎么交付"的标准流程，是所有软件开发团队的项目管理指南。

无论最终产品形态是 Web、App、小程序还是桌面软件（EXE），**其核心流程大体一致，但在技术选型、设计规范、测试重点和发布渠道上会产生显著分歧**——这也是多端项目管理的核心挑战。

## 设计初衷（Motivation）

### 历史演进
- **前身技术**：瀑布模型（1970，Winston Royce）——线性顺序：需求→设计→实现→测试→部署→维护，阶段间不可回溯
- **为什么前身被淘汰**：瀑布模型假设需求在项目初期就能完全锁定，实践中几乎不可能。客户看到产品才意识到真正的需求，但按瀑布模型回头修改的成本是初期的 100 倍以上（"1:10:100 法则"）
- **本模型的核心突破**：现代 SDLC 吸收了敏捷思想，允许每个阶段循环迭代。每个阶段有明确的"输出物"，但阶段间可回溯——这是敏捷 SDLC 与纯瀑布模型的最大区别
- **为什么是它活下来了**：SDLC 不是一个"模型"，而是一套可以根据项目特点裁剪的框架。重型项目（医疗、金融合规）可偏瀑布式严格执行；互联网产品可偏敏捷式快速迭代。这种"可裁剪性"使得 SDLC 成为行业通用语言
- **当前版本**：本文描述的是"敏捷化 SDLC"——保留了瀑布阶段划分的清晰性，但吸纳了 Scrum 的 Sprint 迭代和 DevOps 的持续交付理念

> ⚠️ **版本兼容性**：本概念为通用方法论，不涉及具体技术版本号。各阶段涉及的技术栈版本约束见各自的原子笔记。

### 设计思想
SDLC 解决的根本矛盾是：**软件开发天然具有高不确定性和高复杂度，但企业需要明确的成本、时间和质量预估**。SDLC 通过"分阶段、里程碑化、产出物驱动"的方式，将不可见的思维劳动转化为可度量、可管理的工程过程。其核心设计哲学是：

1. **分而治之**：将模糊的"做一个软件"拆为 8 个有明确输入/输出的阶段
2. **前置风险**：通过"可行性评估"和"原型设计"把最大的不确定性提前暴露
3. **文档即契约**：每个阶段的输出物是下一阶段的输入，降低沟通失真
4. **反馈闭环**：运维阶段的线上数据反映到新一轮需求分析，形成持续迭代

## 实现（Implementation）

### 完整实例：从零启动一个跨平台电商项目
> 以下展示一个跨平台（Web + 小程序 + App）电商项目如何按 SDLC 八阶段推进。

**阶段一：立项与前期准备（Initiation）**
- 决策"做不做"以及"为什么做"
- 核心动作：市场调研与竞品分析（明确目标用户痛点、竞品差异化优势）、可行性评估（商业可行性 ROI、技术可行性、合规法律风险如 GDPR / 个人信息保护法）
- 输出物：《商业计划书（BP）》《竞品分析报告》《项目立项书》

**阶段二：需求分析与产品规划（Requirements）**
- 将抽象的"做一个电商"转化为可执行的功能列表
- 核心动作：需求收集（用户访谈/问卷调查/业务头脑风暴）→ 功能梳理 → 提取 MVP（最小可行产品）→ 优先级排序 → 砍掉伪需求
- 输出物：脑图（产品功能架构图）、业务流程图（如注册登录流程、支付闭环流程）、产品需求文档（PRD）

**阶段三：原型设计与 UI/UX（Design）**
- 将文字需求具象化为可视化界面
- 核心动作：UX 交互设计（Axure/Figma 线框图与低保真原型 + 页面跳转逻辑）、UI 视觉设计（高保真设计图 + 切图 + UI Kit）
- 各端差异在此阶段开始显现（详见 <a href="obsidian://open?file=多端设计规范与技术选型">多端设计规范与技术选型</a>）

**阶段四：架构设计与技术选型（Architecture）**
- CTO/技术负责人根据业务体量和多端需求制定技术路线
- 详见 <a href="obsidian://open?file=多端设计规范与技术选型">多端设计规范与技术选型</a>

**阶段五：敏捷开发与编码（Development）**
- 进入实质性代码编写阶段
- 核心动作：接口定义与 Mock（Apifox/Swagger 锁定 API → 前后端并行开发）、Sprint 迭代（1-2 周为周期，每日站会同步进度）、Code Review（资深工程师审核核心逻辑）、多端协同（后端统一 RESTful/GraphQL API，各端分别调用）

**阶段六：测试与质量保证（Testing）**
- 详见 <a href="obsidian://open?file=多端测试策略与专项测试">多端测试策略与专项测试</a>

**阶段七：部署上线与发布（Deployment）**
- **这是各端差异最大的环节**
- 详见 <a href="obsidian://open?file=多端发布部署与运营维护">多端发布部署与运营维护</a>

**阶段八：运营维护与迭代（Operations & Maintenance）**
- 上线只是开始，真正的考验在落地之后
- 核心动作：线上监控（Bugly 收集 App 崩溃、Sentry 收集前后端报错；神策/友盟/Google Analytics 监控用户留存和漏斗转化率）、Hotfix（Web&服务端可直接发版；App&小程序可通过热更新机制下发补丁）、版本迭代（根据反馈和数据规划 V1.1、V1.2，再次进入"需求→开发→测试→上线"闭环）
