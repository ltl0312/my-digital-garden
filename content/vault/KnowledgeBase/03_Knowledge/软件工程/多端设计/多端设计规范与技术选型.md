# 多端设计规范与技术选型

## 📍 知识体系定位
- **所属技术栈**：软件工程 / 多端项目设计
- **所在层级**：L1 多端项目设计 → 设计规范 + 技术选型
- **上游依赖**：<a href="obsidian://open?file=软件项目全流程-SDLC八阶段模型">SDLC 八阶段模型</a>（第三、四阶段的基础框架）
- **下游延伸**：各端具体技术栈深入学习（Vue 3 / React / Flutter / Spring Boot / Electron 等）
- **同级技术**：单一平台设计规范（纯 Web 设计规范、纯 iOS HIG、纯 Material Design）——多端对比的独特价值在于跨平台差异分析

## 概述（Overview）
> 当一个软件项目需要同时覆盖 Web、App、小程序、桌面端时，设计规范和架构选型不再是"用一种方案打天下"，而是需要根据每个平台的特点、限制和用户习惯，选择差异化的交互规范和最适合的技术栈。

核心问题：同一个产品功能，在不同平台上应该"长什么样"和"用什么技术做"？

## 设计初衷（Motivation）

### 历史演进
- **前身技术**：PC Web 时代（1990s-2000s），一套 HTML/CSS/JS 适配所有桌面浏览器，几乎不考虑移动端；Native App 时代（2008-2015），iOS 和 Android 各自为政，互不兼容，公司需要养两套独立的移动端团队
- **为什么前身被淘汰**：移动互联网爆发后，用户期望在手机、平板、PC 上拥有一致体验，单一平台策略无法覆盖用户触点；纯原生开发成本过高，跨端框架应运而生
- **本方法论的核心突破**：将"各端差异"作为一等关注对象，在项目设计阶段就明确各端的交互差异和共享逻辑边界，避免"先做完 Web 再移植 App"的返工模式
- **为什么是它活下来了**：跨端框架（Flutter / React Native / Uni-app）让"一份代码多端运行"成为可能，但各端的平台差异不会消失——懂得"哪里该统一、哪里该差异化"的设计决策能力比选框架更重要
- **当前版本**：2025-2026 主流跨端生态：Flutter 3.x、React Native 0.76+、Tauri 2.x、Electron 30+、Uni-app (Vue 3)

### 设计思想
多端设计存在一个根本矛盾：**共享逻辑最大化（降成本）vs. 平台体验最优化（提质量）**。全部共享 → 平台体验差（如把网页直接塞进 App）；全部分离 → 3-4 套独立代码，维护成本爆炸。

这催生了"分层共享"的设计思想：
1. **共享层**：业务逻辑、API 调用、数据模型（应尽可能统一）
2. **适配层**：UI 组件库、路由导航、手势交互（各端差异化的主战场）
3. **原生层**：硬件调用、推送通知、应用商店审核（纯平台特定代码）

## 实现（Implementation）

### 完整实例：一个"订单管理功能"在各端的设计决策

#### 一、交互与 UI 设计规范差异

| **平台类型**     | **交互与设计核心关注点**                                     |
| ---------------- | ------------------------------------------------------------ |
| **Web (网页)**   | 响应式设计（适配多尺寸屏幕）、鼠标悬停（Hover）状态、首屏加载视觉体验。 |
| **App (移动端)** | iOS 遵循 Human Interface Guidelines，安卓遵循 Material Design。注重触控区域大小（≥44pt）、手势操作（滑动删除订单、长按多选）。 |
| **小程序**       | 严格受限于宿主（微信/支付宝）的设计规范，顶部导航栏和底部 TabBar 的定制受限。订单列表的"下拉刷新"必须使用宿主提供的 API。 |
| **EXE (桌面端)** | 窗口状态（最大化/最小化/托盘）、多显示器拖拽、右键菜单（订单批量操作）、键盘快捷键支持（Ctrl+N 新建订单）。 |

#### 二、客户端 / 前端技术选型

| **平台类型**       | **主流技术栈推荐**                                           |
| ------------------ | ------------------------------------------------------------ |
| **Web / H5**       | React, Vue.js, Angular (配合 Webpack/Vite 构建)。            |
| **App (原生)**     | iOS: Swift / Objective-C。Android: Kotlin / Java。           |
| **App (跨端)**     | Flutter (高性能，自绘引擎), React Native (生态好，JS 桥接), Uni-app (国内多端通用，小程序/App/H5)。 |
| **小程序**         | 原生语法 (WXML/WXSS), 跨端框架 (Taro, Uni-app)。             |
| **EXE / Mac 软件** | Electron (Web技术栈, 跨平台), Tauri (Rust+Web, 体积小), C#/.NET (Windows独占, 高性能), Qt (C++)。 |

#### 三、服务端与基础设施

- **后端语言**：Java (Spring Boot/Cloud - 适合大型企业级)、Go (高并发)、Node.js (前端全栈友好)、Python (数据与AI驱动型)。
- **数据库**：MySQL/PostgreSQL (关系型核心数据)、Redis (缓存与高频读取)、MongoDB (非结构化文档)。
- **DevOps架构**：Docker 容器化、Kubernetes (K8s) 编排、GitLab CI/CD 自动化构建。

> **💡 补充**：技术选型不是"选最好的"，而是"选最合适的"。判断标准：团队技术栈熟悉度 > 社区生态活跃度 > 性能天花板 > 个人偏好。一个全 Vue 的团队强行选 React "因为更流行"通常是灾难。

### 关键参数/配置说明

| 选型维度 | 关键考量因素 | 推荐决策标准 |
|----------|-------------|-------------|
| 跨端框架选择 | 团队栈、性能要求、国内/海外 | 国内多端（小程序必含）→ Uni-app/Taro；海外高性能 → Flutter；React 团队 → React Native |
| 后端语言选择 | 业务类型、团队栈、并发量 | 企业级/金融 → Java Spring Boot；高并发互联网 → Go；AI/数据分析 → Python |
| 桌面端方案 | 体积要求、性能要求、团队栈 | Web 技术栈团队 → Electron；体积敏感 → Tauri；Windows 独占高性能 → C#/.NET |
| 数据库选择 | 数据结构、读写比例、扩展需求 | 核心交易数据 → MySQL/PostgreSQL；缓存/会话 → Redis；日志/文档 → MongoDB/ES |
