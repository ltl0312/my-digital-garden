# 多端发布部署与运营维护

## 📍 知识体系定位
- **所属技术栈**：软件工程 / DevOps 运维
- **所在层级**：L3 发布运维与持续交付 → 多端发布流程 + 线上监控
- **上游依赖**：<a href="obsidian://open?file=软件项目全流程-SDLC八阶段模型">SDLC 八阶段模型</a>（第七、八阶段的宏观框架）；<a href="obsidian://open?file=多端测试策略与专项测试">多端测试策略与专项测试</a>（测试通过是发布的前置条件）
- **下游延伸**：CI/CD 流水线、蓝绿部署、灰度发布、A/B 测试
- **同级技术**：纯 Web 部署（Nginx + CDN）、纯 App 发布（App Store Connect + Google Play Console）

## 概述（Overview）
> 多端发布部署是整个 SDLC 中**各端差异最大的环节**，也是项目最容易"卡脖子"的阶段。它不仅涉及技术层面的服务器部署、打包上传，还涉及大量非技术流程：应用商店审核、域名备案、代码签名证书购买、特种资质申请等。

上线只是开始，真正的考验在于上线后的**线上监控**与**持续迭代**。

## 设计初衷（Motivation）

### 历史演进
- **前身技术**：物理服务器 + FTP 上传（2000s 早期），App 没有应用商店（越狱/侧载安装）。发布就是"拷贝文件到服务器"，没有审核、没有签名、没有灰度。
- **为什么前身被淘汰**：移动互联网的安全需求催生了应用商店审核机制（2008 Apple App Store 首创）；云计算的普及让部署从"买机器"变成"买服务"；用户对可用性的要求让"上线后没人管"成为不可接受的运维模式
- **本方法论的核心突破**：将多端发布的非技术流程（审核/审核/签名）显式化为可执行清单，避免技术团队"代码写完了但卡在审核/备案上"的尴尬——这是大量项目延期的真实原因
- **为什么是它活下来了**：各端发布规则的碎片化是不可改变的现实（苹果不会因为开发者抱怨就取消审核，工信部不会因为项目着急就跳过备案）——与其抱怨，不如将其纳入项目计划
- **当前版本**：2025-2026 主流发布渠道：Apple App Store ($99/年)、Google Play ($25 一次性)、微信小程序（300 元认证/年）、各安卓厂商应用商店（华为/小米/OPPO/VIVO）

### 设计思想
多端发布的核心矛盾：**各端的"闸门"完全不同**——Web 无闸门（即时生效），小程序有轻闸门（1-3 天机器+人工审核），App 有重闸门（iOS 1-3 天人工审核极易因 IAP 被拒，Android 需在多商店反复打包上传），桌面端有信任闸门（杀毒软件误杀需要 EV 证书建立信任）。

解决思路：**并行推进**。不要等所有端都开发完才去弄发布——Web 可以最早上线（无审核），小程序审核和 Android 各商店审核可以并行准备，iOS 审核留足缓冲时间（至少预留 1 周审核 + 可能的 1-2 次拒绝修改）。

## 实现（Implementation）

### 完整实例：跨平台电商项目发布全景图

#### 一、服务端部署（后台 — 各端共用）

1. 购买云服务器（阿里云、AWS、腾讯云等）。**选型考量**：国内用户 → 阿里云/腾讯云（需备案）；海外用户 → AWS/GCP/Azure（免备案）
2. 域名备案（国内必须，周期约 1-2 周）。**关键前置**：备案期间网站不能访问，需提前规划时间
3. 配置 SSL 证书（HTTPS 加密，App 和小程序强制要求）。推荐 Let's Encrypt（免费自动化）或云厂商托管证书
4. 数据库迁移、Nginx 负载均衡配置

#### 二、各端发布流程与坑点

| **平台类型**      | **上线流程与注意事项**                                       |
| ----------------- | ------------------------------------------------------------ |
| **Web**           | 静态资源上传 CDN，服务器更新配置。**即时生效，无审核**。     |
| **小程序**        | 在微信公众平台提交代码审核。**注意：** 涉及医疗、社交、视频等需提供特种资质（如ICP证），否则会被拒审。提交前在"开发版"充分测试。 |
| **App (iOS)**     | 申请 Apple 开发者账号（$99/年），通过 Xcode 上传 App Store Connect 提交审核。**坑点：** 苹果审核极严（通常 1-3 天），虚拟商品必须接入苹果内购（IAP）并交 30% 苹果税。**常见被拒原因**：缺少隐私政策链接、权限申请无说明、UI 太像网页套壳。 |
| **App (Android)** | 国内需上架各大手机厂商应用商店（华为、小米、OPPO、VIVO 等），需准备软著（软件著作权）。**坑点**：各商店标准不一，需分别打包（不同签名/不同应用 ID），部分商店要求 ICP 备案。 |
| **EXE (Windows)** | 购买 EV 代码签名证书（防止被杀毒软件误杀拦截，否则 Windows Defender 会弹"未知发布者"警告）。使用 Inno Setup 或 NSIS 制作 `.exe` 安装包，配置自动更新（OTA）逻辑。发布在官网供用户下载。 |

> **💡 补充**：iOS 的 30%"苹果税"仅针对**虚拟商品/服务**（游戏充值、会员订阅、在线课程）。实物商品（电商、外卖、打车）不收取。如果你的 App 同时卖实体商品和虚拟会员，会员部分必须走 IAP。这是苹果审核最容易踩的坑。

#### 三、运营维护与迭代（上线后的持续工作）

1. **线上监控**：
   - **异常收集**：Bugly 收集 App 崩溃堆栈（Android/iOS），Sentry 收集前后端报错（含用户操作回溯）
   - **数据分析**：神策/友盟/Google Analytics 监控用户留存率、漏斗转化率（如"浏览商品 → 加入购物车 → 提交订单 → 支付成功"每一步的流失率）
2. **热更新（Hotfix）**：
   - Web 和服务端 → 直接发版修复（即时生效）
   - App 和小程序 → 如果无法等待商店审核（通常 1-3 天），可通过 React Native/小程序的热更新机制直接下发补丁包
   - **⚠️ 注意**：iOS 热更新不能改变 App 的核心功能，否则会被视为"绕过审核"而下架
3. **版本迭代**：根据用户反馈和数据指标，规划 V1.1, V1.2 版本，再次循环进入"需求分析 → 开发 → 测试 → 上线"的完整闭环

### 关键参数/配置说明

| 发布环节 | 关键工具/平台 | 耗时预估 | 核心风险 |
|----------|-------------|---------|---------|
| 域名备案 | 阿里云/腾讯云备案系统 | 1-2 周 | 信息填写错误被打回重审 |
| SSL 证书 | Let's Encrypt / 云厂商 | 即时-2 天 | 证书过期忘记续期（建议自动续期） |
| 小程序审核 | 微信公众平台 | 0.5-3 天 | 缺少特种资质（社交/医疗/视频类） |
| iOS 审核 | App Store Connect | 1-3 天 | IAP 被拒、隐私政策不合规 |
| Android 上架 | 各厂商开发者平台 | 1-7 天 | 软著未办、各商店标准不一致 |
| 代码签名 | DigiCert / Sectigo EV 证书 | 1-5 天 | 证书过期 → 杀软误杀拦截 |
