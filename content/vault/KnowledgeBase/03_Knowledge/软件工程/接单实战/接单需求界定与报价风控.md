# 接单需求界定与报价风控

## 📍 知识体系定位
- **所属技术栈**：软件工程 / 自由职业
- **所在层级**：L4 自由职业与接单实战 → 需求管理与商务风控
- **上游依赖**：<a href="obsidian://open?file=自由职业接单全流程指南">自由职业接单全流程指南</a>（全流程框架中的第三、四阶段）
- **下游延伸**：<a href="obsidian://open?file=接单交付安全与防骗机制">接单交付安全与防骗机制</a>（合同约定的付款条件决定交付策略）
- **同级技术**：企业级需求管理（PRD/用户故事）、产品经理的需求分析方法论

## 概述（Overview）
> 接单中最核心的商务环节：如何将客户的模糊描述转化为**有边界的功能清单**，基于清单估算工时、给出报价，并通过合同和分段付款机制保护自己的劳动不被白嫖。

需求界定和报价是决定这个项目**是赚钱还是亏本（亏时间）**的关键。技术再好的开发者，如果在需求阶段没锁死边界，后期就会被无限的需求蔓延（Scope Creep）拖死。

## 设计初衷（Motivation）

### 历史演进
- **前身模式**：口头报价（"这个项目大概 X 万"）→ 开发 → 客户持续加需求 → 开发者不好意思拒绝 → 越做越亏 → 烂尾或撕破脸
- **为什么前身被淘汰**：口头约定没有约束力。开发者和客户对"完成"的定义完全不同——开发者认为功能跑通了就是完成，客户认为"我想象中的所有细节都实现"才是完成
- **本模式的突破**：用**功能清单（Excel/黑白线框图）**替代口头描述，把双方对"完成"的理解白纸黑字对齐。核心创新是"需求边界不是讨论出来的，是写出来并双方签字确认的"
- **为什么 3-4-3 分段付款是行业标准**：30% 定金覆盖前期投入（需求分析 + 原型 + 架构搭建），40% 进度款覆盖主体开发，30% 尾款覆盖收尾 + 部署 + 文档。任何阶段客户毁约，开发者都不亏——定金亏了不亏，进度款亏了不亏，只有尾款阶段跑路才会亏，但此时你已经拿到了 70%
- **当前阶段**：2024-2026 电子合同平台（法大大、上上签、腾讯电子签）降低了签约门槛，个人开发者也可以低成本获得法律保障

### 设计思想
需求界定与报价机制解决的根本矛盾：**客户想要"花确定的钱得到不确定的结果"（尽可能多），开发者想要"花不确定的时间得到确定的收入"（尽可能稳）**。解决方案是把双方的不确定性都锁定在合同中：

1. **功能清单 = 需求的确定性**：清单之外不做的，清单之内必须做的
2. **报价公式 = 成本的确定性**：工时 × 时薪 + 硬件成本 + 风险溢价，每个数字都有依据
3. **3-4-3 付款 = 现金流的确定性**：每个阶段双方都有退出期权（但退出有代价）
4. **变更收费 = 边界的弹性**：新增需求可以，但要走变更流程并加钱，不是"顺便改一下"

## 实现（Implementation）

### 完整实例：为一个"校园二手交易小程序"做需求界定与报价

#### Step 1: 界定需求边界
不要只听客户口头描述。你必须帮客户把想法落实成简单的**功能列表（Excel）**或**黑白线框图**。双方必须对着明确的功能清单确认："我们只做清单上的这些，新增功能需要加钱"。

**功能清单示例（部分）**：

| 功能模块 | 功能描述 | 是否包含 |
|----------|---------|---------|
| 用户注册/登录 | 微信一键授权登录 | ✅ |
| 商品发布 | 上传图片（最多9张）、填写标题/价格/描述 | ✅ |
| 商品搜索 | 按关键词搜索、按分类筛选、按价格排序 | ✅ |
| 聊天功能 | 买家卖家实时聊天 | ✅ |
| 支付功能 | 微信支付 | ✅ 含微信支付商户号申请协助 |
| 商家认证 | 上传营业执照审核 | ❌ 不在本期范围 |
| AI 智能推荐 | 根据浏览记录推荐商品 | ❌ 后期可追加报价 |

> **💡 补充**：最关键的一张表不是"要做什么"，而是"不做什么"。"不做的"写在合同里和"要做的"一样重要——当你拒绝客户的额外需求时，你可以指着合同说"这不在这张清单上"。

#### Step 2: 工时评估与报价
- **拆解任务**：将项目拆解为前端页面、后端接口、数据库设计等模块
- **评估工时**：预估每个模块所需的开发小时数。务必结合自身的日常时间安排（如日常课业、考试周等）留出至少 **20%-30% 的缓冲时间**
- **报价公式**：`(总预估工时 × 你的时薪) + 服务器/域名等硬件成本 + 风险溢价`

**实战示例**：

| 模块 | 预估工时 | 备注 |
|------|---------|------|
| 前端 15 个页面 | 40h | 含 UI 还原 |
| 后端 20 个接口 | 35h | 含数据库设计 |
| 微信支付集成 | 10h | 含商户号申请调试 |
| 联调 + 部署 | 15h | 含 Docker 化 |
| 缓冲（25%） | 25h | 需求变更 + 返工 |
| **合计** | **125h** | |

> 假设时薪 150 元/h，服务器域名成本 500 元，风险溢价 10%：
> 报价 = (125 × 150) + 500 + 1875 ≈ **21,000 元**

#### Step 3: 签订合同
无论金额大小，**必须签合同**（电子合同亦可），明确以下内容：
- **交付时间**：从收到定金之日起 X 个工作日内完成
- **验收标准**：以双方确认的功能清单为准，功能跑通且无阻塞性 Bug
- **付款节点**：按什么比例、什么时间节点付款
- **售后期限**：免费维保期的时长和范围

#### Step 4: 定金与分段付款
**绝对不要在收到定金前写一行代码！**

- **常规付款比例**：通常采用 **3-4-3** 或 **4-4-2** 比例。
  - **30% 定金**：签完合同，收到定金后正式开工。这 30% 覆盖你做需求分析 + 原型设计 + 架构搭建的时间成本
  - **40% 进度款**：核心功能开发完毕，客户验收演示后支付。客户可以看到一个可运行的版本（部署在你的测试服务器上）
  - **30% 尾款**：项目全部完成，交付源码和部署上线**前**支付。注意：是"部署前支付"，不是"部署后支付"

> **💡 补充**：为什么尾款要在"交付源码前"而不是"部署上线后"？因为源码一旦交出去，你就丧失了唯一的谈判筹码。客户拿到源码后拖着不给尾款，你没有任何反制手段。

### 关键参数/配置说明

| 要点 | 推荐做法 | 原因 |
|------|---------|------|
| 缓冲比例 | 20%-30% | 软件开发天然有不确定性，0 缓冲 = 必然延期 |
| 新手时薪参考 | 100-200 元/h（国内）| 按技术水平、项目复杂度调整。在校生可酌情降低 |
| 最低起接金额 | ≥ 5000 元 | 低于此金额的项目不值得启动合同和流程成本 |
| 定金比例 | ≥ 30% | 低于 30% 的定金无法覆盖前期投入，风险过高 |
| 合同形式 | 电子合同（法大大/腾讯电子签）| 法律效力等同纸质合同，且不可抵赖 |
| 售后维保期 | 1-3 个月 | 过长会变成免费劳动力，过短客户不愿签 |
