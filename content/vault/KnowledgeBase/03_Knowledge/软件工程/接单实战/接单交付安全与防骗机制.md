# 接单交付安全与防骗机制

## 📍 知识体系定位
- **所属技术栈**：软件工程 / 自由职业
- **所在层级**：L4 自由职业与接单实战 → 交付安全与防骗
- **上游依赖**：<a href="obsidian://open?file=自由职业接单全流程指南">自由职业接单全流程指南</a>（全流程第六、七阶段的宏观背景）、<a href="obsidian://open?file=接单需求界定与报价风控">接单需求界定与报价风控</a>（合同约定的付款条件决定了交付策略）
- **下游延伸**：维权知识（合同纠纷诉讼/仲裁的基本流程）
- **同级技术**：企业级代码资产保护（代码混淆/数字水印/许可证管理），但接单场景更依赖流程风控而非技术手段

## 概述（Overview）
> 接单交付安全是在客户付清全款之前，通过**流程控制**（而非技术手段）保护自己的劳动成果不被白嫖或窃取的一套机制。核心原则只有一条：**在钱没到账之前，不给客户任何"可以绕过你"的机会**。

这是保护自己劳动成果的最后一道防线。技术上再完美的项目，如果在交付环节被客户套路，前面的所有努力都白费。

## 设计初衷（Motivation）

### 历史演进
- **前身模式**：做完直接发源码 → 客户收到后拉黑不付尾款 / 客户说"这个不符合预期"要求退款（但代码已经在对方手里了）
- **为什么前身被淘汰**：源码是开发者的唯一谈判筹码。交出去之后，客户没有任何动力配合结算。这不是信任问题，是**博弈论问题**——在一次性交易中，双方都会选择对自己最有利的策略，而"拿到源码后不付款"是客户的占优策略
- **本模式的突破**：将代码的"使用权"和"所有权"分离——客户在付清全款前只拥有在开发者服务器上的测试使用权，付清全款后才转移完整源码的所有权。这个设计不是"不信任客户"，而是"不给不诚信的客户留下可乘之机"
- **为什么"Docker 打包交付"是新趋势**：传统的"传源码 + 帮忙部署"模式有两大问题：① 客户环境千奇百怪，部署期间免费当运维；② 源码交出去后如果出问题，客户会说是你没有部署好。Docker 镜像交付将环境问题隔离——"在我机器上能跑，在你机器上通过 Docker 也能跑，环境问题与我无关"
- **当前阶段**：2024-2026 接单防骗策略演进——部分客户学会了用"公司审计要求""投资方要看代码""要做安全评估"等理由索要源码。这些理由有些是真的，有些是套路。判断标准：**他们是否愿意为此提前支付进度款**

### 设计思想
交付安全的底层博弈逻辑：

1. **代码 = 筹码**：在一次性外包交易中，代码是开发者唯一的议价能力。一旦交出，博弈结束，开发者从"需要被满足的乙方"变成"可被忽略的乙方"
2. **信息不对称的双面性**：合同签订前，客户对技术的无知是你的劣势（需求沟通成本高）；但代码写完后，客户对技术的无知是你的优势（他们无法独立修改和维护代码，必须依赖你）
3. **验收标准的前置锁定**：如果验收标准在合同中已经以"功能清单"形式锁定，那么"不满意"就不等于"没完成"。只有"功能清单上的功能没有按约定实现"才算未完成

## 实现（Implementation）

### 完整实例：校园二手交易小程序的交付安全策略

#### 防线一：使用自己的测试服务器
在客户付清尾款之前，**必须**将项目部署在你自己控制的云服务器和域名下供客户测试。

> **原因**：如果部署到客户服务器，客户就有了完整的代码运行环境。即使你不给源码，客户也可以通过服务器上的文件拿到编译后的代码，或者直接找另一个开发者"逆向"你的工作。你的服务器 = 你的控制权。

```bash
# 你的测试环境（完全由你控制）
# 域名：test-yourproject.yourdomain.com
# 服务器：你的阿里云/腾讯云账号
# 数据库：你创建的只读账号给客户测试
# 客户只能通过浏览器访问 → 看不到源码、拿不到数据库、无法转移部署
```

#### 防线二：绝不提前交源码
无论客户以什么理由（"老板要看代码""需要审计""投资方要做技术尽调""要给我们技术总监评估一下"），在**全款到账前，坚决不交付完整源码、数据库管理员账号或部署到对方提供的服务器上**。

常见套路与应对：

| 客户说 | 潜台词 | 正确回应 |
|--------|--------|----------|
| "老板要看一下代码质量" | 拿到源码后可能找别人接手 | "我可以在屏幕共享下展示代码结构和关键模块，但不交付源码文件" |
| "投资方要做技术尽调" | 同上 | "请投资方列出具体关注点，我准备一份技术架构说明文档 + 核心模块的截图/录屏" |
| "部署到我们服务器上测试一下" | 拿到运行环境后改密码/断你连接 | "全款到账前统一在我的测试服务器上验收。生产部署是交付阶段的最后一步" |
| "先给我们源码，我们把尾款流程走了" | 尾款流程可能无限期"走"下去 | "合同约定尾款到账 → 交付源码。请先完成付款流程" |

#### 防线三：Bug 修复与变更管控
客户在测试服务器上点检，提出修改意见。对照前期的功能清单，分类处理：

- **属于 Bug 的**：免费修。Bug 的定义是"功能清单上承诺的功能实际运行结果与描述不符"
- **属于新需求的**：要求追加预算。"这个想法很好，我们可以在二期里实现它。我先给你一个二期报价"
- **属于"体验不好"的灰色地带**：小修小改（< 2h）可以做，但务必让客户知道"这个超出了合同范围，这次我帮你免费做了"。这是为了维护关系——但绝不养成"说了就能免费做"的预期

#### 防线四：尾款结算与正式交付
按以下顺序执行，**顺序不能乱**：

1. **收到尾款**：确认最后一笔资金进入你的账户（不是"打了"，是"到账了"）
2. **物料移交**：
   - 将前端静态资源和后端可执行文件部署到客户的服务器上
   - 将系统通过 **Docker 镜像**的形式打包，连同数据库脚本一起交付，确保对方能在任何环境快速重启
   - 发送包含源码的压缩包或转移代码仓库权限
   - 交付简单的《操作手册》或接口文档
3. **售后交接**：告知客户免费维保期的起止日期和范围

```bash
# Docker 镜像打包交付（标准交付物）
docker save your-project-backend:latest | gzip > backend-image.tar.gz
docker save your-project-frontend:latest | gzip > frontend-image.tar.gz

# 交付包内容：
# ├── backend-image.tar.gz      # 后端 Docker 镜像
# ├── frontend-image.tar.gz     # 前端 Docker 镜像
# ├── docker-compose.yml        # 一键启动配置
# ├── init.sql                  # 数据库初始化脚本
# ├── 操作手册.md                # 运维文档
# └── 源码.zip                  # 完整源码（尾款到账后才交付）
```

### 关键参数/配置说明

| 风控要点 | 推荐做法 | 风险 |
|----------|---------|------|
| 测试服务器 | 自己的云服务器 + 自有域名 | 客户服务器 = 失控 |
| 源码交付时机 | 尾款到账后 | 提前交 = 丧失议价权 |
| 演示方式 | 屏幕共享/录屏，不传文件 | 录屏可保留，文件不可控 |
| Bug 判定标准 | 以功能清单为准 | 口头约定 = 无限 Bug |
| 交付物格式 | Docker 镜像优先 | 避免环境差异扯皮 |
| 数据库账号 | 测试期只给只读账号 | 管理员账号 = 数据可被导出 |
