## 概述（Overview）
> 一句话定义：Git 是一种**分布式版本控制系统**（Distributed Version Control System, DVCS），由 Linux 之父 Linus Torvalds 开发，用于追踪软件项目源代码的修改历史，支持多人协作、代码共享和代码重构。每个开发者都拥有本地代码库的**完整副本**，可以离线工作。

Git 的基本工作流程如下：

1. 创建一个 Git 仓库（repository），用于存储代码和版本历史记录。
2. 通过 `git add` 命令将更改的文件添加到 Git 的暂存区（staging area）中。
3. 通过 `git commit` 命令将暂存区中的更改提交到 Git 仓库中，并生成一个新的版本号（commit hash）。
4. 如果需要撤销某个提交，可以使用 `git revert` 命令创建一个新的提交，抵消先前的提交效果。
5. 如果需要合并不同分支的代码，可以使用 `git merge` 命令进行合并。
6. 如果需要查看代码的历史提交记录，可以使用 `git log` 命令获取详细信息。
7. 如果需要将代码推送到远程仓库，可以使用 `git push` 命令。
8. 如果需要从远程仓库获取代码，可以使用 `git pull` 命令拉取到本地。

### Git 四大工作区域

```text
工作区 (Workspace / Working Directory)
    ↓  git add
暂存区 (Index / Stage)
    ↓  git commit
本地仓库 (Local Repository)
    ↓  git push / git pull / git fetch
远程仓库 (Remote Repository)
```

- **Workspace（工作区）**：你电脑文件系统上实际修改文件的目录。在这里创建、编辑和删除文件。
- **Index / Stage（暂存区）**：中间状态，充当提交更改的缓冲区。必须明确将文件添加到暂存区，才能提交到版本库——这让你可以对每个更改进行精细控制。
- **Repository（仓库区/本地仓库）**：包含 Git 存储库的所有历史记录和元数据，是 Git 存储库的核心组成部分，由 Git 自动维护。
- **Remote（远程仓库）**：托管在网络上的仓库副本（如 GitHub、GitLab、Gitee），用于团队间共享代码。

> **💡 补充**：工作区、暂存区、版本库之间的区别在于——你可以对工作区中的任何文件进行修改，但只有将它们添加到暂存区并提交到版本库后，它们才会成为 Git 跟踪的部分。

## 设计初衷（Motivation）

### 历史演进
- **前身技术**：在 Git 出现之前（2005 年以前），Linux 内核社区使用商业工具 **BitKeeper** 进行版本控制。更早还有 **CVS**（1990）和 **SVN/Subversion**（2000）等集中式版本控制系统。
- **为什么前身被淘汰**：2005 年 BitKeeper 的免费版使用权被收回，Linux 社区急需一个替代品。而 SVN 等集中式系统存在**单点故障**问题——中央服务器宕机则所有人无法工作；分支操作笨重，合并痛苦。
- **本技术的核心突破**：
  - **分布式架构**：每个开发者拥有完整仓库副本，无需网络即可提交、查看历史、创建分支。
  - **基于内容寻址**：使用 SHA-1 哈希值标识每个提交（而非 SVN 的递增数字），保证提交的全局唯一性和数据完整性。
  - **快照而非差异**：Git 将每次提交视为整个项目的快照（snapshot），而非文件差异（delta），这使得分支切换和版本对比极快。
  - **轻量级分支**：创建分支只是创建一个 41 字节的指针文件，几乎零成本。
- **为什么是它活下来了**：同类分布式工具（Mercurial、Bazaar、Darcs）中，Git 因 Linux 内核社区的背书、GitHub 的生态推动（2008 年上线）、以及极致的性能表现而成为事实标准。如今 Git 占据版本控制系统 90%+ 的市场份额。
- **当前版本**：Git 2.45+（2024 年），持续活跃开发中。

> ⚠️ **版本兼容性**：本文所有命令基于 Git 2.23+。Git 2.23 引入了 `git switch` 和 `git restore` 作为 `git checkout` 职责拆分的新命令。本文同时列出新旧两种写法。

### 设计思想

Git 的设计哲学可以概括为三个核心原则：

1. **分布式优先（Offline-First）**：每个克隆都是完整备份。你可以在飞机上提交 50 次，落地后一次性推送。这从根本上消除了集中式系统的单点故障和网络依赖。

2. **内容不可变（Content Immutability）**：一旦提交，commit 的 SHA-1 哈希就永远不变。如果你想"修改历史"，Git 实际上是创建新的提交并移动指针，而非修改已有数据。这保证了审计追溯的可靠性。

3. **显式操作为默认（Explicit Over Implicit）**：Git 不会自动帮你做任何事——你必须显式 `add` 才能暂存，显式 `commit` 才能记录。这种"不猜测用户意图"的设计虽增加了学习曲线，但避免了自动化带来的意外数据丢失。

## SVN 与 Git 的区别

| 维度 | Git | SVN |
|------|-----|-----|
| **架构** | 分布式：每个开发者拥有完整副本 | 集中式：所有开发者共享中央代码库 |
| **离线能力** | 完整支持，可离线提交和查看历史 | 需要网络连接才能进行版本控制操作 |
| **分支** | 轻量级，创建/合并几乎零成本 | 重量级，创建/合并耗时且占资源 |
| **版本号** | SHA-1 哈希值（40 位十六进制），保证全局唯一 | 递增数字版本号，简单直观但有冲突风险 |
| **数据完整性** | 每个开发者拥有完整备份，中央仓库损坏可从任意克隆恢复 | 所有数据存于中央，损坏可能导致数据丢失 |
| **性能** | 更快：基于内容的哈希检测修改 | 较慢：需要检查文件元数据（时间戳和大小） |
| **学习曲线** | 较陡峭，概念多 | 较平缓，命令更直观 |

总之，虽然 SVN 和 Git 都是版本控制系统，但它们的设计和实现方式存在较大差异。开发人员应根据自身需求选择最适合的版本控制系统。现代软件开发中，Git 已是事实标准。
