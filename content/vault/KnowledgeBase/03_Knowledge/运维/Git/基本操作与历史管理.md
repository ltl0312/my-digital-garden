# Git 基本操作与历史管理

## 📍 知识体系定位
- **所属技术栈**：DevOps / 运维
- **所在层级**：Git 版本控制 → 日常操作层
- **上游依赖**：<a href="obsidian://open?file=分布式版本控制核心概念">Git 分布式版本控制核心概念</a> — 必须先理解工作区/暂存区/版本库模型
- **下游延伸**：<a href="obsidian://open?file=分支管理与合并策略">Git 分支管理与合并策略</a> — 基本操作熟练后进入分支管理
- **同级技术**：SVN 的 checkout/update/commit 工作流（集中式，概念模型不同）

## 概述（Overview）
> 一句话定义：Git 基本操作是指开发者在日常编码中使用频率最高的一组命令——从创建仓库、暂存修改、提交历史，到查看状态、回退版本、撤销误操作。这些命令构成了 Git 使用者的"肌肉记忆"。

## 设计初衷（Motivation）

### 历史演进
- **前身技术**：SVN 的工作流是 `checkout → modify → update → commit`，只有工作区和中央仓库两层。
- **为什么前身被淘汰**：SVN 缺少暂存区概念，修改后直接提交，无法精细控制每次提交的内容范围。
- **本技术的核心突破**：Git 在两阶段提交中插入了**暂存区**，可选择性地暂存文件中的部分修改（`git add -p`），将一次工作区的多处修改拆分为多个语义清晰的提交。
- **当前版本**：Git 2.23 引入 `switch` 和 `restore` 拆分 `checkout` 的职责。

### 设计思想
**暂存区的哲学意义**：暂存区让"保存进度"和"记录历史"成为两个独立操作。工作区的修改是混乱无序的，暂存区让你在 `commit` 之前有一次"整理"的机会——挑选哪些修改应该放在同一个提交里，哪些应该分开。

## 实现（Implementation）

### 仓库创建与文件追踪

```bash
# ① 场景：在空目录中初始化一个 Git 仓库
mkdir my-project && cd my-project
git init
# ② git init 在当前目录创建 .git 隐藏目录，存储所有版本数据

# ① 场景：将文件纳入 Git 版本管理
echo "Hello Git" > README.md
git add README.md           # 将工作区的修改添加到暂存区
git commit -m "chore: initial commit"
# ③ 预期输出：[main (root-commit) a1b2c3d] chore: initial commit

# ① 场景：一次性添加当前目录所有修改到暂存区
git add .
# ② . 表示当前目录及子目录下的所有修改（新增、修改、删除）

# ① 场景：交互式暂存——只添加文件中的部分修改（强烈推荐！）
git add -p
# ② Git 会逐个 hunk 询问：y(暂存) / n(不暂存) / s(拆分) / e(手动编辑)
```

### 查看状态与历史

```bash
git status                   # 查看工作区和暂存区状态
git status -s                # 简洁模式：?? 未跟踪, M 已修改, A 已暂存
git log                      # 按时间倒序列出所有提交
git log --oneline --graph --all  # 单行简洁历史 + ASCII 分支图
git log --since="2 weeks ago"    # 最近两周的提交
git log --stat               # 显示每个提交的文件变更统计
git log -p                   # 显示每个提交的完整 diff
```

### 提交操作进阶

```bash
# ① 场景：跳过暂存区，直接提交所有已跟踪文件的修改（不添加新文件）
git commit -am "fix: 修复登录页样式问题"

# ① 场景：提交信息的最佳实践格式（Conventional Commits）
git commit -m "feat: 添加用户登录功能
>
> - 实现 JWT 认证
> - 添加登录页面
> - 优化错误处理"
# ③ 常见类型：feat / fix / docs / refactor / test / chore
```

### 版本回退

```bash
# ① 场景：撤销上次提交，保留修改在工作区（最安全）
git reset --soft HEAD~1
# ② --soft：只移动 HEAD，暂存区和工作区不变

# ① 场景：撤销上次提交和暂存，保留修改在工作区（默认行为）
git reset --mixed HEAD~1
# ② --mixed：移动 HEAD + 清空暂存区，工作区不变

# ① 场景：完全撤销（危险！）
git reset --hard HEAD~1
# ② --hard：移动 HEAD + 清空暂存区 + 覆盖工作区。⚠️ 永久删除

# ① 场景：安全回退已推送的提交
git revert HEAD
# ② 生成新提交来"反向操作"，不改写历史
```

### 撤销修改与删除文件

```bash
# 放弃工作区修改（Git >= 2.23 推荐语法）
git restore <filename>
# 旧语法：git checkout -- <filename>

# 取消暂存
git restore --staged <file>    # 新语法（推荐）
git reset HEAD <file>           # 旧语法

# 修改最后一次提交
git commit --amend -m "新的提交信息"
git add forgotten_file && git commit --amend --no-edit  # 补充遗漏文件

# 删除文件
git rm <filename>               # 同时从工作区和暂存区删除
git rm --cached <filename>      # 从跟踪中移除但保留本地文件
```
