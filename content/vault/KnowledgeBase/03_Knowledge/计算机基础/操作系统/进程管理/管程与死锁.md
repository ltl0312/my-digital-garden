# 第一部分：管程

## 概述（Overview）
> 管程（Monitor）是一种高级同步机制，将共享数据和对数据的操作封装在一个模块内，由编译器保证互斥，让程序员无需手动编写 PV 操作。

### 管程的组成
```
monitor 管程名 {
    ① 局部于管程的共享数据结构说明
    ② 对该数据结构进行操作的一组过程（函数）
    ③ 对局部共享数据设置初始值的语句
}
// 管程 ≈ 类（Class）；过程 ≈ 方法（Method）
```

### 管程的三大特征
1. 局部数据只能被管程内的过程访问
2. 进程只有通过调用管程内的过程才能进入管程访问共享数据
3. 每次仅允许一个进程在管程内执行某个内部过程（互斥由编译器负责实现）

## 实现（Implementation）

### 管程解决生产者-消费者问题

```
monitor ProducerConsumer
    condition full, empty;        // 条件变量实现同步（排队）
    int count = 0;                // 缓冲区产品数

    void insert(Item item) {      // 放入产品
        if (count == N)
            wait(full);           // 缓冲区满，等待
        count++;
        insert_item(item);
        if (count == 1)
            signal(empty);        // 通知消费者"有产品了"
    }

    Item remove() {               // 取出产品
        if (count == 0)
            wait(empty);          // 缓冲区空，等待
        count--;
        if (count == N - 1)
            signal(full);         // 通知生产者"有空位了"
        return remove_item();
    }
end monitor;

// 调用
producer() { while(1) { item = 生产产品; ProducerConsumer.insert(item); } }
consumer() { while(1) { item = ProducerConsumer.remove(); 消费(item); } }
```

# 第二部分：死锁

## 概述（Overview）
> 死锁（Deadlock）：在并发环境下，各进程因竞争资源而造成互相等待对方手里的资源，导致各进程都阻塞、都无法向前推进的现象。

### 死锁 vs 饥饿 vs 死循环

| 现象 | 本质 | 范围 | 责任方 |
|------|------|------|--------|
| **死锁** | 互相等待对方资源，都阻塞 | 至少两个进程 | OS（管理者） |
| **饥饿** | 长期得不到所需资源 | 可能单个进程 | OS（管理者） |
| **死循环** | 跳不出某个循环 | 可能单个进程 | 程序员（被管理者） |

## 设计初衷（Motivation）

### 死锁产生的四个必要条件（缺一不可）

| 条件 | 含义 |
|------|------|
| **互斥条件** | 只有对必须互斥使用的资源的争抢才会导致死锁 |
| **不剥夺条件** | 进程获得的资源在未使用完前不能被强行夺走 |
| **请求和保持条件** | 保持已有资源，又请求新资源，新资源被占→阻塞但不放已有资源 |
| **循环等待条件** | 存在进程-资源的循环等待链 |

> ⚠️ 发生死锁时一定有循环等待，但发生循环等待时未必死锁（循环等待是死锁的必要不充分条件）。

### 死锁的三种处理策略

```
预防死锁 ── 破坏四个必要条件之一（静态策略）
避免死锁 ── 银行家算法，防止进入不安全状态（动态策略）
检测解除 ── 允许死锁发生，定期检测并解除
```

## 实现（Implementation）

### 策略一：预防死锁——破坏四个条件

| 破坏目标 | 方法 | 缺点 |
|----------|------|------|
| 互斥条件 | SPOOLing 技术把独占设备改造成共享设备 | 并非所有资源都可改造 |
| 不剥夺条件 | 得不到新资源时释放已有资源 | 实现复杂、可能造成前一阶段失效 |
| 请求和保持条件 | 静态分配：运行前一次性申请全部资源 | 资源利用率低、可能饥饿 |
| 循环等待条件 | 顺序资源分配法：资源编号，按编号递增请求 | 不便增加新设备、编程麻烦 |

### 策略二：避免死锁——银行家算法

```
核心思想：在资源分配前预判此次分配是否会导致系统进入"不安全状态"

数据结构：
  Available[m]  — 当前可用资源数
  Max[n×m]      — 各进程最大需求
  Allocation[n×m] — 已分配的资源
  Need[n×m]     — 还需多少资源 (= Max - Allocation)

步骤：
  1. 检查 Request ≤ Need       (不超过声明的最大需求)
  2. 检查 Request ≤ Available  (系统有足够可用资源)
  3. 试探分配，更新数据结构
  4. 执行安全性算法 → 检查是否存在安全序列
     → 存在安全序列：正式分配
     → 不存在安全序列：拒绝请求，进程等待
```

> **安全序列**：按某种顺序分配资源，每个进程都能顺利完成。存在安全序列 = 系统处于安全状态 = 一定不会死锁。

### 策略三：死锁检测与解除

**资源分配图检测算法**：依次消除与不阻塞进程相连的边，直到无边可消。若能消去所有边 → 可完全简化 → 无死锁。

**解除死锁的方法**：
1. **资源剥夺法**：挂起某些死锁进程，抢占其资源分配给其他进程
2. **撤销进程法**：强制撤销部分/全部死锁进程
3. **进程回退法**：回退到还原点
