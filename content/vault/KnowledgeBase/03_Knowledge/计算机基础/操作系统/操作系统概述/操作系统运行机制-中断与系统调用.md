# 操作系统运行机制、中断与系统调用

## 📍 知识体系定位
- **所属技术栈**：计算机基础 / 操作系统
- **所在层级**：XD-2 操作系统 → 操作系统概述 → 运行机制
- **上游依赖**：<a href="obsidian://open?file=CPU">计算机组成原理-CPU</a> — PSW 寄存器、指令周期、特权指令是理解 CPU 状态切换的前置知识
- **下游延伸**：<a href="obsidian://open?file=同步与锁机制">Java 多线程同步与锁</a> — JVM 层面的锁实现依赖 OS 内核提供的互斥机制
- **同级技术**：异常处理（Java/C++ 的 try-catch 是语言层面的异常，OS 的异常指 CPU 检测到的执行错误）

## 概述（Overview）
> 操作系统通过 CPU 的两种状态（内核态/用户态）和中断机制，实现对系统资源的安全管理和 CPU 使用权的控制。系统调用是应用程序请求 OS 内核服务的唯一合法入口。

**核心三要素**：
1. **两类指令**：特权指令（只允许内核使用）vs 非特权指令（应用程序可用）
2. **两种状态**：内核态（可执行特权指令）vs 用户态（只能执行非特权指令）
3. **状态切换**：用户态→内核态由中断触发（硬件自动完成）；内核态→用户态由修改 PSW 完成

## 设计初衷（Motivation）

### 历史演进
- **前身技术**：单道批处理系统，监督程序常驻内存，无 CPU 状态区分
- **为什么前身被淘汰**：用户程序可随意访问硬件资源，系统安全无法保障；程序死循环时 CPU 无法被回收
- **本技术的核心突破**：CPU 硬件层面划分特权级（Ring 0~3），中断机制让 OS 能强行夺回 CPU 控制权
- **为什么是它活下来了**：特权级隔离是现代多用户、多任务操作系统的安全基石，至今所有主流 OS 都依赖此机制

### 设计思想
根本矛盾：**用户程序需要访问资源 vs 系统需要保护资源不被滥用**。解决方案是"代理人模式"——内核是唯一能操作硬件的"代理人"，应用程序必须通过系统调用请求内核代为操作。中断是内核从用户程序手中"夺回 CPU 使用权"的唯一途径。

### 跨学科溯源

## 实现（Implementation）

### 中断的分类

```
中断
├── 内中断（异常、例外）—— 与当前指令有关，来源于 CPU 内部
│   ├── 陷入（trap）：应用程序主动触发，如执行陷入指令发起系统调用
│   ├── 故障（fault）：可被修复的错误，修复后归还 CPU 使用权
│   └── 终止（abort）：致命错误，无法修复，不归还 CPU 使用权
│
└── 外中断（狭义中断）—— 与当前指令无关，来源于 CPU 外部
    ├── 时钟中断：时钟部件每隔一个时间片发送，实现多道程序并发
    └── I/O中断：IO 任务完成时发送
```

### 系统调用过程（以创建文件为例）

```
应用程序调用 fopen("test.txt", "w")
        │  ← 用户态
        ▼
库函数封装系统调用参数（文件名、模式等）
        │
        ▼
执行陷入指令（trap）── 触发内中断
        │  ← CPU 硬件自动切换为内核态
        ▼
OS 内核中断处理程序：
  ① 根据系统调用号查系统调用表
  ② 执行 sys_open() 内核函数
  ③ 在磁盘上创建文件、分配 FCB
        │
        ▼
返回文件描述符给应用程序
        │  ← 切换回用户态
        ▼
应用程序拿到 fd，继续执行
```

> ⚠️ **关键点**：陷入指令在用户态执行，执行后立即引发内中断使 CPU 进入核心态。发出系统调用请求是在用户态，对系统调用的处理在核心态下进行。

### 系统调用 vs 库函数

| 对比维度 | 系统调用 | 库函数 |
|----------|----------|--------|
| 运行态 | 核心态执行 | 用户态执行（可能触发系统调用） |
| 与 OS 关系 | OS 内核直接提供 | 编程语言封装 |
| 例子 | `sys_open()` | `fopen()`（封装了 `sys_open`） |
| 范围 | 库函数 > 系统调用 | 有的库函数涉及系统调用（如 fopen），有的不涉及（如 abs） |
