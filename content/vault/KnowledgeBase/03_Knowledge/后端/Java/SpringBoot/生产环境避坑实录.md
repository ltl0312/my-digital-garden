## 一、CORS Preflight：OPTIONS 预检请求 401

### 死亡重现
```
现象：
  ① 登录接口 (GET /api/login) → 正常，返回 200
  ② 点击"新增用户" (POST /api/user，携带 Authorization Header) → 控制台爆红 CORS Error
  ③ 查看后端日志：拦截器报 401 "未携带 Token"

原因：
  浏览器在发送"复杂请求"之前，会先发一个 OPTIONS 预检请求探路。
  这个 OPTIONS 请求：
    - 不携带 Authorization Header（即使是 Axios 拦截器加上的）
    - 不携带 Cookie
    - Content-Type 不是 application/json（而是 Access-Control-Request-Headers）

  当 JwtInterceptor 拦截到这个 OPTIONS 请求 → 发现没有 Token → 返回 401
  浏览器收到 401 的预检响应 → 主请求直接取消 → CORS Error
```

### 什么是"复杂请求"？

| 条件 | 简单请求 | 复杂请求 |
|------|----------|----------|
| Method | GET / HEAD / POST | PUT / DELETE / PATCH |
| Content-Type | `text/plain` / `multipart/form-data` / `application/x-www-form-urlencoded` | **`application/json`** ← 绝大多数 API！ |
| 自定义 Header | 无 | **`Authorization`** ← JWT 必带！ |

> 只要符合复杂请求任一条件，浏览器就会先发 OPTIONS 预检。

### 排雷方案

```java
// 方案一：JWT 拦截器对 OPTIONS 无条件放行（最简单有效）
@Component
public class JwtInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, ...) {
        if ("OPTIONS".equalsIgnoreCase(request.getMethod())) {
            return true;  // ← 血泪教训，必须放行！
        }
        // 正常 Token 校验...
    }
}

// 方案二：配置全局 CORS 过滤器
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOriginPatterns("*")
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600);  // 预检响应缓存 1 小时，减少 OPTIONS 请求
    }
}
```

## 二、数据库连接池耗尽：循环中查数据库

### 死亡重现
```java
// ❌ 杀手级代码：循环中逐条查询
public List<UserVO> getUserList(List<Long> idList) {
    List<UserVO> result = new ArrayList<>();
    for (Long id : idList) {               // 假设 idList 有 1000 个元素
        User user = userService.getById(id);  // 每次循环一次数据库连接！
        result.add(convert(user));
    }
    return result;
}
// 后果：1000 次网络 I/O + 1000 次连接池获取/归还 → 连接池瞬间抽干 → 整个系统卡死
```

### 排雷方案
```java
// ✅ 正确写法：一次 IN 语句搞定
public List<UserVO> getUserList(List<Long> idList) {
    List<User> users = userService.listByIds(idList);  // WHERE id IN (...)
    return users.stream().map(this::convert).toList();
}
```

### 连接池参数调优参考

| 参数 | 建议值 | 说明 |
|------|--------|------|
| `maximumPoolSize` | 20~50 | 不宜过大（过大给 DB 压力），不宜过小（并发不足） |
| `minimumIdle` | 5~10 | 空闲维持连接数 |
| `connectionTimeout` | 30000ms | 等待连接超时，过长会雪崩 |
| `idleTimeout` | 600000ms | 空闲连接超时回收 |
| `maxLifetime` | 1800000ms | 连接最大存活时间（需小于 MySQL 的 wait_timeout） |

## 三、Spring @Transactional 事务失效三大场景

### 场景 1：代理被绕过（最常见）

```java
@Service
public class UserService {
    // 外部调用：proxy.createUser() → 事务生效 ✅
    @Transactional
    public void createUser(UserDTO dto) {
        userMapper.insert(user);
        this.sendEmail(user);  // ← this 调用！绕过代理！
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)  // 期望新事务
    public void sendEmail(User user) {
        // 但这里的事务设置完全没生效！因为是通过 this 调用的，不是代理对象
    }
}
```

```java
// ✅ 修复：将 sendEmail 抽离到独立类，或使用 AopContext
@Service
public class UserService {
    @Autowired
    private EmailService emailService;  // ← 注入独立 Bean

    @Transactional
    public void createUser(UserDTO dto) {
        userMapper.insert(user);
        emailService.sendEmail(user);  // ← 通过 Spring 代理调用，事务生效 ✅
    }
}
```

### 场景 2：异常被吞掉

```java
// ❌ 异常被 catch 吞了，Spring 没感知 → COMMIT 而不是 ROLLBACK
@Transactional
public void updateUser(UserDTO dto) {
    try {
        userMapper.updateById(user);
        thirdPartyApi.call();  // 第三方调用抛异常
    } catch (Exception e) {
        log.error("更新失败", e);
        // ← 这里没有 throw！异常被吞了！
        // Spring 认为一切顺利 → 执行 COMMIT → 脏数据留在数据库
    }
}

// ✅ 修复：catch 后必须抛出异常（或手动回滚）
@Transactional
public void updateUser(UserDTO dto) {
    try {
        userMapper.updateById(user);
        thirdPartyApi.call();
    } catch (Exception e) {
        log.error("更新失败", e);
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();  // 手动回滚
        throw new BusinessException("更新用户失败", e);
    }
}
```

### 场景 3：非 public 方法

```java
// ❌ Spring AOP 默认只代理 public 方法
@Transactional
private void internalUpdate() {  // private → 事务不生效！
    userMapper.updateById(user);
}

// ❌ 同类的 protected 和 package-private 也可能不生效（取决于代理方式）
```

### @Transactional 失效自查清单

| 原因 | 表现 | 修复 |
|------|------|------|
| this 调用 | 同类方法调用绕过代理 | 抽离到独立 Bean 或 AopContext |
| 异常被吞 | catch 后不抛出 | 手动回滚 + 重新抛出 |
| 非 public | private/protected 方法 | 改为 public |
| 数据库引擎不支持 | MyISAM 引擎 | 改用 InnoDB |
| `rollbackFor` 不匹配 | 默认只回滚 RuntimeException | `@Transactional(rollbackFor = Exception.class)` |
