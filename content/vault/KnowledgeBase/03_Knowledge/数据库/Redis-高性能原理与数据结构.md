## 核心概念
> Redis 单机 10 万+ QPS 的惊人吞吐量来源于三个核心设计：纯内存操作、单线程事件循环（Reactor + epoll）、以及针对不同场景优化的高效底层数据结构。

## 一、Redis 高性能的三大基石

### 1. 纯内存操作
```
机械硬盘随机读写：~100 IOPS
SSD 随机读写：    ~100,000 IOPS
内存读写：        纳秒级延迟，百万倍于磁盘

Redis 所有数据都在内存中，持久化是异步的 (RDB/AOF append)
```

### 2. 单线程事件循环（Reactor 模型）

> Redis 核心处理逻辑是单线程的——**彻底避免了多线程上下文切换的性能损耗和死锁问题**。

```
        ┌──────────── client1 ────────────┐
        │  ┌──────── client2 ────────┐    │
        │  │ ┌────── clientN ───┐    │    │
        ▼  ▼ ▼                  ▼    ▼    ▼
     ┌────────────────────────────────────┐
     │         epoll (内核多路复用)         │  一个线程监听数千个 socket
     │   当某个 socket 可读时 → 通知 Redis │
     └────────────────┬───────────────────┘
                      │ 事件到达
     ┌────────────────▼───────────────────┐
     │         Redis 主线程                │  单线程：串行处理命令
     │  GET key  →  查字典 →  返回 value   │  无竞态、无锁、无上下文切换
     └────────────────────────────────────┘
```

**epoll 工作原理简析：**
```
传统的 select/poll：每次调用都要把所有 fd 从用户态拷贝到内核态，O(N) 遍历
epoll：在内核空间维护一个事件表，通过回调机制，只有活跃的 fd 才通知应用层

比喻：
  select → 老师一个个点名："你到了吗？"（即使 99% 的人都没变）
  epoll  → 每个学生到教室后自己举手，老师只看举手的
```

### 3. 高效底层数据结构

| 数据结构 | 底层实现 | 时间复杂度 | 典型场景 |
|----------|----------|-----------|----------|
| String | SDS（简单动态字符串） | O(1) | Token、验证码、计数器 |
| Hash | 哈希表 + 压缩列表 | O(1) | 用户信息缓存、局部更新 |
| List | 双向链表 + 压缩列表 | O(1) 头尾操作 | 消息队列、时间线 |
| Set | 哈希表 + 整数集合 | O(1) | 标签、共同好友 |
| **ZSet** | **跳表 (SkipList) + 哈希表** | O(log N) | 排行榜、延时队列 |

## 二、ZSet 与跳表（SkipList）深度剖析

### 为什么 ZSet 选择跳表而非红黑树？

```
跳表 = 多层索引链表：

Level 3:  [1] ──────────────────────→ [50]  ← 高层索引，跳跃大
Level 2:  [1] ──────→ [25] ────────→ [50] ──────→ [75]  ← 中层索引
Level 1:  [1] → [10] → [25] → [35] → [50] → [62] → [75] → [90]  ← 底层全量

查找 [62]：
  从顶层开始：1 → 50 → 发现 50 < 62，继续
            50 → 降一层，50 → 75，发现 75 > 62，退回到 50
            降一层，50 → 62 → 找到！

查找复杂度：O(log N)，与红黑树相同
```

### 跳表 vs 红黑树 在 Redis 中的选型

| 维度 | 跳表 | 红黑树 |
|------|------|--------|
| 实现复杂度 | ⭐ 简单 | ⭐⭐⭐ 复杂（旋转变色） |
| 范围查询 | ⭐⭐⭐⭐⭐ 天然支持（底层链表） | ⭐⭐ 需要中序遍历 |
| 内存占用 | 稍大（多层索引指针） | 较小 |
| 并发友好 | ⭐⭐⭐⭐ 局部修改 | ⭐⭐ 旋转影响大范围 |

> Redis 作者 antirez 的选择理由："跳表实现更简单，且范围查询场景下表现更好。"

## 三、全栈开发 Redis 五大典型场景

### String 类型

```bash
# ① Token 鉴权（带 TTL 自动过期）
SETEX token:user:1001 7200 "eyJhbGciOi..."

# ② 短信验证码（5分钟过期）
SETEX sms:13800138000 300 "123456"

# ③ 高并发计数器（原子操作）
INCR article:read:2026      # 文章阅读量 +1
INCRBY user:score:1001 10   # 用户积分 +10

# ④ 分布式锁
SET lock:order:1001 unique_value NX EX 30
# NX = 不存在才设置，EX 30 = 30 秒自动释放
```

### Hash 类型
```bash
# 缓存用户信息（可局部更新某个字段）
HSET user:1001 name "张三" age "28" email "zhangsan@example.com"
HGET user:1001 name          # "张三"
HINCRBY user:1001 age 1      # age +1
HDEL user:1001 email         # 删除邮箱字段
```

### ZSet 类型
```bash
# 排行榜：记录用户活跃度分数
ZADD daily:active 100 user:1001  # 用户1001 活跃度 100
ZADD daily:active 85  user:1002
ZADD daily:active 120 user:1003

# 获取 Top 10
ZREVRANGE daily:active 0 9 WITHSCORES

# 获取用户排名
ZREVRANK daily:active user:1001   # 返回第几名（从0开始）

# 统计分数区间内的用户数
ZCOUNT daily:active 80 120
```

## 四、Redis 缓存三大经典问题

| 问题 | 描述 | 解决方案 |
|------|------|----------|
| **缓存穿透** | 查询不存在的数据，每次都穿透到 DB | ① 缓存空值（TTL 较短）② 布隆过滤器 |
| **缓存击穿** | 热点 key 过期瞬间大量请求打到 DB | ① 热点 key 永不过期 ② 互斥锁（SETNX）只允许一个线程查 DB |
| **缓存雪崩** | 大量 key 同时过期 + Redis 宕机 | ① TTL 加随机值（避免同时过期）② 主从 + 哨兵高可用 |
