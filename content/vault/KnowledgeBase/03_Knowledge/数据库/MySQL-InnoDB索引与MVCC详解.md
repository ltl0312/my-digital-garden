## 核心概念
> InnoDB 引擎凭借 B+ Tree 索引实现"千万级数据三次磁盘 I/O 内定位"，通过 MVCC（多版本并发控制）实现"读写互不阻塞"。两者共同构成了 MySQL 高性能和高并发的基石。

## 一、B+ Tree 索引：为什么不用 Hash 或二叉树？

### 三种索引结构的本质差异

| 数据结构 | 查询速度 | 范围查询 | 树高（1000万条） | 磁盘 I/O 次数 |
|----------|----------|----------|------------------|---------------|
| **Hash** | O(1) | ❌ 不支持（数据散列后无序） | 无 | ~1 次 |
| **二叉/红黑树** | O(log n) | ✅ 支持 | ~23 层 | ~23 次 |
| **B+ Tree** | O(log n) | ✅ 完美支持（叶子节点双向链表） | **~3 层** | **≤ 3 次** |

### B+ Tree 的精妙设计

```
                     ┌─────────────────────┐
                     │    根节点（内存）     │  只存索引键，不存数据
                     │  [100]  [500]  [900] │  一个 16KB 节点可存 1000+ 键
                     └──┬──────┬──────┬─────┘
              ┌─────────┘      │      └─────────┐
              ▼                ▼                ▼
     ┌────────────┐   ┌────────────┐   ┌────────────┐
     │ [1~99]     │   │ [101~499]  │   │ [501~899]  │   ← 中间节点（内存/磁盘）
     │ . . .      │   │ . . .      │   │ . . .      │
     └──┬──┬──┬──┘   └──┬──┬──┬──┘   └──┬──┬──┬──┘
        │  │  │         │  │  │         │  │  │
   ┌────┘  │  └────┐    │  │  │    ┌────┘  │  └────┐
   ▼       ▼       ▼    ▼  ▼  ▼    ▼       ▼       ▼
  [叶子节点] [叶子节点] [叶子节点]  ← 存放完整行数据（聚簇索引用）
  │ 1 张三  │ │ 2 李四 │ │ 3 王五 │  ← 双向链表连接，支持范围扫描
  └─────────┘ └─────────┘ └─────────┘
```

**关键设计决策：**
- **非叶子节点只存键** → 一个 16KB 磁盘页可装入上千个键 → 树极矮
- **叶子节点存全部数据** → 找到叶子节点就拿到了数据
- **叶子节点用双向链表连接** → `BETWEEN 100 AND 500` 只需定位起点，然后沿着链表顺序扫描

### 为什么 3 层 B+ Tree 能支撑 2000 万行？
```
假设：
  - 一行数据 ≈ 1KB
  - 一个 16KB 磁盘页 ≈ 16 行数据（叶子节点）
  - 一个 16KB 磁盘页 ≈ 1200 个键（非叶子节点，假设每个键 + 指针 ≈ 13 Byte）

  第 1 层（根）：1 页 → 1200 个指针
  第 2 层：    1200 页 → 1200 × 1200 = 1,440,000 个指针
  第 3 层（叶）：1,440,000 页 → × 16 行/页 ≈ 2300 万行

任何查询最多 3 次磁盘 I/O！
```

## 二、聚簇索引 vs 二级索引

### 结构差异

| 类型 | 叶子节点存什么 | 数量限制 | 查找路径 |
|------|--------------|----------|----------|
| **聚簇索引** |**完整行数据** | 每表 1 个 | 索引 → 直接拿到数据 |
| **二级索引** | **聚簇索引键值** | 多个 | 索引 → 主键值 → 回表查聚簇索引 |

### 回表查询
```sql
-- 假设 id 是聚簇索引，name 列上建了二级索引
SELECT * FROM user WHERE name = '张三';

执行过程：
  ① 在 name 的二级索引 B+ Tree 中找到 '张三' → 拿到对应的 id = 100
  ② 用 id = 100 去聚簇索引 B+ Tree 中查找 → 拿到完整行数据
  ← 这就是"回表"，多了一次 B+ Tree 查找

如何避免回表？
  ③ 只需 SELECT id, name FROM user WHERE name = '张三'
     → 二级索引叶子节点内已经存了 (name, id)，无需回表
     ← 这就是"覆盖索引"
```

## 三、MVCC：多版本并发控制

### 核心问题
> 张三修改数据时，李四同时读取数据——如何做到互不阻塞？

### MVCC 的三件套

```
每行数据有两个隐藏字段：
  ┌─────────────┬─────────────┬──────────────┬──────────────┐
  │  业务字段    │ DB_TRX_ID   │ DB_ROLL_PTR  │ DB_ROW_ID    │
  │  (id, name) │ 事务版本号   │ 回滚指针      │ 隐藏主键      │
  └─────────────┴─────────────┴──────────────┴──────────────┘

Undo Log 版本链：
  ┌──────────────────────────────────────────────┐
  │  当前最新版本 (DB_TRX_ID=300)                  │
  │  id=1, name='新名字', DB_ROLL_PTR ──────────┐ │
  └──────────────────────────────────────┬───────┘ │
                                         │         │
  ┌──────────────────────────────────────▼───────┐ │
  │  旧版本 (DB_TRX_ID=200)                      │ │
  │  id=1, name='旧名字', DB_ROLL_PTR ──────────┐│ │
  └──────────────────────────────────────┬───────┘│ │
                                         │        │
  ┌──────────────────────────────────────▼───────┐│
  │  更旧版本 (DB_TRX_ID=100)                    ││
  │  id=1, name='初始名', DB_ROLL_PTR = NULL    ││
  └──────────────────────────────────────────────┘│
```

### Read View：一致性视图

```
当李四在可重复读（RR）隔离级别下查询时：

① MySQL 为李四的事务生成一个 Read View
   - 记录当前活跃事务列表（未提交的事务 ID）
   - 记录当前最大事务 ID

② 李四读 id=1 时：
   - 先看最新版本 (DB_TRX_ID=300)
   - 300 在李四的 Read View 中是不可见的（在创建 Read View 时未提交）
   - 沿着 DB_ROLL_PTR 链找上一个版本 (DB_TRX_ID=200)
   - 200 在 Read View 中是可见的 → 返回 '旧名字'

最终效果：李四读到的始终是他事务开始时已提交的数据，
          张三的修改（未提交）不会影响李四→ "读写分离，互不阻塞"！
```

### 四种隔离级别下的 MVCC 行为

| 隔离级别 | Read View 生成时机 | 效果 |
|----------|-------------------|------|
| READ UNCOMMITTED | 不使用 MVCC | 读到未提交数据（脏读） |
| READ COMMITTED | 每次查询都生成新的 Read View | 每次读到最新已提交数据（不可重复读） |
| **REPEATABLE READ** | **事务开始时生成一次** | 整个事务看到同一个快照（MySQL 默认） |
| SERIALIZABLE | 锁表 | 完全不并发 |
