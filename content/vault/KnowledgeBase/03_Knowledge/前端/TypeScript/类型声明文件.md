# TypeScript 类型声明文件与 declare

## 📍 知识体系定位
- **所属技术栈**：前端 Vue 3
- **所在层级**：L3 工程化 → TypeScript → 工程配置
- **上游依赖**：<a href="obsidian://open?file=基础与特殊类型">TypeScript-基础与特殊类型</a>、<a href="obsidian://open?file=接口与函数类型">TypeScript-接口与函数类型</a>（声明文件里的内容就是这些类型语法）
- **下游延伸**：库作者发布 npm 包、JS 项目迁移 TS、Vue 项目 `env.d.ts` 配置
- **同级技术**：Flow 的 libdefs、Java 的 `.class` 字节码接口描述（概念类比）

## 概述（Overview）
> TS 存在两种文件：**`.ts` 文件（代码实现文件）**——既包含类型信息，又包含可执行代码，可被编译为 `.js` 执行；**`.d.ts` 文件（类型声明文件）**——只包含类型信息，不会生成 `.js`，仅为 JS 提供类型描述。`declare` 关键字用于声明"其他地方已存在的变量"的类型，而不是创建新变量。

## 设计初衷（Motivation）

### 历史演进
- **前身技术**：JS 生态中每个库都是"无类型"的——引入 lodash/axios 后，TS 只能看到 `any`，开发者失去全部智能提示和编译期检查。
- **为什么前身被淘汰**：TS 需要理解第三方代码的类型，但 JS 源码本身没有类型标注，也无法强制所有库重写。
- **本技术的核心突破**：类型声明文件把"类型"与"实现"彻底解耦——`axios` 的 JS 实现保持原样，旁边放一个 `axios.d.ts` 描述它的类型，TS 自动加载两者合并。类型信息成为独立可分发、可共享的资产。
- **为什么是它活下来了**：生态协作模式成熟——库自带声明（TS 自动加载）；不自带的由社区 **DefinitelyTyped**（GitHub 仓库）维护，安装 `@types/包名` 后 TS 也会自动加载。这套机制让 TS 兼容了整个 JS 生态。
- **当前版本**：TypeScript 5.x。`moduleResolution` 决定声明文件的查找策略（node16/bundler 等）。

### 设计思想
`.d.ts` 是 TS 的"接口层"设计——**实现（.js/.ts）与描述（.d.ts）分离**，让"为已有 JS 提供类型"成为可能，也让库作者可以发布"仅类型"的包。`declare` 关键字严格区分"声明已有事物"与"创建新事物"：对于 `type`/`interface` 等纯 TS 类型（只能用在 TS 中），可以直接省略 `declare`；对于 `let`/`function` 等具有双重含义（JS 和 TS 都可用）的声明，必须用 `declare` 明确指出"这里只是类型声明，不要生成代码"。

### 跨学科溯源
- 类型声明文件 → <a href="obsidian://open?file=XD-4 编程语言与编译">XD-4 编程语言与编译</a>（头文件思想：C/C++ 的 `.h` 头文件声明与 `.c` 实现分离，TS 的 `.d.ts` 是同一理念的现代化）

## 实现（Implementation）

### 完整实例：从"使用已有声明"到"创建自己的声明"

```typescript
// ========== ① 使用已有的类型声明文件 ==========
// 内置类型：TS 为 JS 运行时所有标准化内置 API（Array/Math/DOM...）都提供了声明文件
const nums: number[] = [1, 2, 3];
nums.map(n => n * 2);                 // ✅ 无需任何配置，lib.es5.d.ts 等自动加载

// 第三方库：库自带声明 → TS 自动加载（如 axios、Vue 3）
import axios from "axios";
// node_modules/axios/index.d.ts 被自动加载，axios.get() 有完整类型

// 无自带声明 → DefinitelyTyped 安装 @types 包，TS 同样自动加载
// npm install -D @types/lodash   →  node_modules/@types/lodash/index.d.ts 生效

// ========== ② 创建自己的声明：项目内共享类型 ==========
// index.d.ts 中定义并 export 共享类型
// export interface ApiResult<T> { code: number; data: T; }
// 其他 .ts 文件中 import 使用（.d.ts 后缀导入时直接省略）
// import { ApiResult } from "./types";   // 实际加载 types.d.ts

// ========== ③ 为已有 JS 文件提供类型声明 ==========
// 场景：JS 项目迁移 TS、成为库作者、TS 项目中混用 .js
// 在导入 .js 文件时，TS 会自动加载与 .js 同名的 .d.ts 文件

// legacy.js 的内容：export function calc(a, b) { return a + b; }
// 与之同名的 legacy.d.ts：
// export function calc(a: number, b: number): number;

// ========== ④ declare 关键字的正确用法 ==========
// ❌ 错误：declare 用于声明"已经存在的变量"，而不是创建新变量
// declare let version: string;    // 如果 JS 里根本没有 version，这就是谎报

// ✅ 正确：为"其他地方（如全局 JS 文件）已存在的变量"声明类型
// globals.js 中已有：window.myConfig = { theme: 'dark' }
declare global {
    interface Window {
        myConfig: { theme: string };   // 为 window 上已有的属性补类型
    }
}
// 纯 TS 类型（type/interface）可省略 declare；
// let/function 等双重含义关键字必须显式 declare，防止 TS 误以为要生成代码
```

### declare 关键字速查

| 声明目标 | 是否必须 declare | 原因 |
|----------|------------------|------|
| `type` / `interface` | ❌ 可省略 | 纯 TS 类型，JS 中不存在对应物 |
| `let` / `const` | ✅ 必须 | 与 JS 变量声明同形，需区分"声明类型"而非"创建变量" |
| `function` | ✅ 必须 | 与 JS 函数声明同形，同理 |
| `class` | ✅ 必须 | 与 JS 类声明同形 |
| `namespace` / `module` | ✅ 必须 | 声明已有模块的结构 |

> **💡 补充**：Vue 3 项目中的 `env.d.ts`（或 `shims-vue.d.ts`）就是典型应用——为 `.vue` 单文件组件模块声明类型；`tsconfig.json` 的 `declaration: true` 可以让 TS 在编译时自动为你的 `.ts` 文件生成 `.d.ts`（库作者发布类型包的标准方式）。`include`/`types` 字段控制哪些声明文件被加载。
