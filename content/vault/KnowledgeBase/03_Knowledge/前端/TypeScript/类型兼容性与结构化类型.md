# TypeScript 类型兼容性与结构化类型系统

## 📍 知识体系定位
- **所属技术栈**：前端 Vue 3
- **所在层级**：L3 工程化 → TypeScript → 类型系统
- **上游依赖**：<a href="obsidian://open?file=接口与函数类型">TypeScript-接口与函数类型</a>（接口的形状检查就是结构化兼容）、<a href="obsidian://open?file=类与高级类型">TypeScript-类与高级类型</a>
- **下游延伸**：类型声明文件设计、泛型约束推导、Vue 3 Props 类型建模
- **同级技术**：Java/C# 的名义类型系统（Nominal Typing）、Python 的结构化类型（`Protocol`）

## 概述（Overview）
> TS 采用**结构化类型系统（Structural Typing）**——类型检查关注的不是"两个类型叫什么名字"，而是"值所具有的形状（结构）"。只要结构匹配（成员齐全、类型对应），不同类型名之间可以互相赋值。这与 Java/C# 的**名义类型系统**（必须显式声明继承/实现关系）截然相反。

## 设计初衷（Motivation）

### 历史演进
- **前身技术**：JavaScript 的鸭子类型（Duck Typing）——"如果它走起来像鸭子、叫起来像鸭子，那它就是鸭子"，运行时看形状不看标签。
- **为什么前身被淘汰**：鸭子类型在运行时才暴露错误，没有编译期检查。
- **本技术的核心突破**：TS 把"看形状不看名字"的思想静态化了——编译器在编译期就按结构检查类型，既保留了 JS 的灵活哲学，又获得编译期安全。
- **为什么是它活下来了**：结构化类型是 JS 生态的自然延续。如果 TS 用名义类型，大量无类型 JS 代码（结构巧合相同的对象）迁移时会爆炸式报错；结构化类型让"形状相同即可兼容"的迁移路径平缓。它是 JS 场景下唯一能让类型系统"不劝退"的选择。
- **当前版本**：TypeScript 5.x。`strictFunctionTypes`（TS 2.6+）使函数参数默认走逆变检查。

### 设计思想
结构化类型系统的本质是：**类型是值的集合（集合论视角）**。`Point` 类型 = "所有拥有 `x: number; y: number` 形状的值"的集合。一个 `Point3D` 值（拥有 x、y、z）必然也属于 Point 集合，所以 `Point3D` 可以赋值给 `Point`——**成员多的可以赋值给成员少的**（子集关系）。这既是 TS 最直观的规则，也是初学者最常见的困惑来源。

## 实现（Implementation）

### Class 与接口的兼容性

```typescript
// ① 结构相同 → 完全兼容（两个不同名的类可以互相赋值）
class Point { x: number; y: number; constructor(x: number, y: number) { this.x = x; this.y = y; } }
class Point2D { x: number; y: number; constructor(x: number, y: number) { this.x = x; this.y = y; } }

const p: Point = new Point2D(1, 2);   // ✅ TS 只看结构，不看类名
// 输入：两个结构相同的类 → 输出：赋值成功

// ② 成员多 → 赋值给成员少（Point3D 拥有 x/y/z，是 Point 的子集超集）
class Point3D { x: number; y: number; z: number; constructor(x: number, y: number, z: number) { this.x = x; this.y = y; this.z = z; } }

const p2: Point = new Point3D(1, 2, 3);   // ✅ 成员多的可以赋值给成员少的
// const p3: Point3D = p;                 // ❌ Error: 成员少的不能赋给成员多的（缺 z）

// ③ 接口之间、接口与 class 之间同样遵循"成员多赋给成员少"
interface IShape { area(): number; }
class Circle { area(): number { return Math.PI; } radius = 1; }
const s: IShape = new Circle();           // ✅ class 实现接口无需 implements 声明
```

### 函数之间的兼容性

```typescript
// ① 参数个数：参数少的可以赋值给参数多的（省略用不到的参数很常见）
type TwoArgs = (a: number, b: number) => void;
const oneArg: (a: number) => void = (a) => console.log(a);
const fn: TwoArgs = oneArg;               // ✅ 参数少的赋给参数多的
// 运行时调用 fn(1, 2)，多余的 2 被忽略——JS 本身允许少用参数

// ② 参数类型：原始类型要求相同；对象类型依然成员多赋给成员少
const numFn: (x: number) => void = (x: number) => {};
const strFn: (x: string) => void = (x: string) => {};
// numFn 不能赋给 strFn（原始类型 number ≠ string）

interface Shape { w: number }
const shapeFn: (s: Shape) => void = (s: Shape) => {};
const squareFn: (s: Shape & { h: number }) => void = (s) => {};
const target: (s: Shape) => void = squareFn;  // ✅ 对象参数：成员多的函数赋给参数要求少的

// ③ 返回值类型：原始类型要求相同；对象类型成员多的可赋给成员少的
const returnsShape: () => Shape = () => ({ w: 1 });
const returnsSquare: () => Shape & { h: number } = () => ({ w: 1, h: 2 });
const assigned: () => Shape = returnsSquare;  // ✅ 返回对象成员多的赋给返回成员少的
```

> **💡 补充**：函数参数方向的反直觉之处——class/接口是"成员多→成员少"兼容，函数参数是"参数少→参数多"兼容，方向相反。原因：函数是消费者，能处理"更少参数"的函数放入"期待更多参数"的位置时，多余参数会被安全忽略（JS 运行时行为）；而返回值是生产者，产出更丰富的对象总能被消费。TS 2.6 起的 `strictFunctionTypes` 让**函数类型**的参数走严格的逆变检查（仅函数声明/表达式，方法 method 仍保持双变以保证兼容性）。
