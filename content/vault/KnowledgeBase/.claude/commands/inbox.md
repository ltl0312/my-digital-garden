## 模式自动识别（路由规则，按优先级从上到下匹配）

1. `$1` 包含 `--tag` 或用户明确要求"批量加标签" → **模式四：批量标签初始化**
2. `$1` 指向 `.pdf` 文件 → **模式三：PDF 文献深度解析**
3. `$1` 指向 `.cpp` / `.h` / `.hpp` / `.c` / `.txt` (代码类) → **模式二：C++ 注释逆向提取**
4. `$1` 指向 `.md` 文件或未提供参数 → **模式一：标准深度整理**（默认）

> 若 `$1` 未提供参数：先执行 `ls 00_Inbox` 扫描待处理文件，按找到的第一个文件类型自动选择模式。

## 全局铁律（所有模式适用，本指令最高优先级）

### 铁律 A：忠实原文，补充而非改写
1. 源文件的措辞、比喻、行文节奏，只要是清晰有效的，**一律保留**。不要用你自己的写作风格替换作者的语气。
2. 源文件中的代码示例，无论大小，**全部原样保留**。如果一个概念有 3 个示例，3 个都保留。缺失的示例才由你补充。
3. 你的任务是"填坑"——源文件缺少的定义、原理、背景，你来补充。源文件已经讲清楚的部分，**不要动**。
4. 需要追加见解时，用 `> **💡 补充**：` 引用块形式，不要直接改写原文。
5. 处理后读者应能分辨"原作者的观点"和"AI 补充的讲解"。如果全篇读起来都是 AI 风格，就是过度改写了。

### 铁律 B：知识体系隔离
- 每篇笔记 YAML 中必须声明 `知识体系` 字段，严格按照 `03_Knowledge/技术划分.md` 填写。
- Java/C++/前端/数据库各有自己的技术体系，不可混用。例如 Java 的 MVC（Spring MVC + JSP/Thymeleaf）与前端 MVC（Vue Router + Components）是完全不同的实现体系。
- 关联上下文的主关联必须在同一知识体系内，跨体系关联仅放在"跨学科溯源"中。

### 铁律 C：版本标注
- YAML 中必须声明 `技术版本` 字段。
- 所有代码示例、配置方案、API 调用必须在标注版本下可运行。
- **绝对不允许不兼容版本的技术混用**（如 Spring Boot 2.x 的 javax.* 与 3.x 的 jakarta.*）。
- 跨学科知识点（操作系统原理、数学概念、设计模式等）不受版本约束。

### 铁律 D：双文档生成（模式四除外）
每处理一个技术概念/独立逻辑块，必须生成**两篇**关联文档：
- **文档一（知识笔记）**：使用对应模式的模板。
- **文档二（配置指南）**：使用统一的配置指南模板。

> **模式专属追加**：
> - 模式二（C++）：铁律 A 追加 "即使某个工具函数很简单，也要为它生成一篇独立笔记。"
> - 模式二（C++）：铁律 B 强调 "C++ 算法/数据结构有自己独立的知识体系。"
> - 模式三（PDF）：source 字段指向母体笔记而非源文件。

### 铁律 E：链接双轨制——图谱防环的根本机制

生成笔记时，**只有底部 `📂 所属` 行可以使用 `[[...]]` 双括号**。其余所有链接——正文引用、前置知识、横向对比、上下游依赖、跨领域关联——一律使用：

> `<a href="obsidian://open?file=文件名">显示文字</a>`

**为什么**：`[[...]]` 在 Obsidian 图谱中产生边，`obsidian://open` 不产生边。全库只有叶子→父节点的 `📂 所属` 边，图谱天然是一棵向根汇聚的树，**永远不可能成环**。

| 链接方向 | 允许格式 | 图谱可见 |
|----------|----------|----------|
| 叶子 → 父 MOC（`📂 所属`） | `[[...]]` | ✅ 可见 |
| 正文所有引用（前置知识、横向对比、跨领域等） | `obsidian://open` | ❌ 不可见 |

> **严禁 P3 同级双向环**：两篇同级笔记互相引用（A↔B），无论用什么格式，一律禁止。发现后拆除其中一个方向的链接。

# 模式二：C++ 注释逆向提取与拆分（处理 .cpp / .h / .hpp / .c / .txt）

## 核心处理工作流

**第一步：逻辑分块与注释剥离**
1. 读取源文件，**判断是否包含多个独立的函数、类或算法逻辑**。如果存在，强制切割为多个独立逻辑块，分别后续处理。
2. 对每个逻辑块，严格区分注释：
   - **独立成行的注释**（`//` 或 `/* ... */`）：提取为纯净自然语言，放入笔记正文。
   - **行尾注释**（跟在代码后的 `//`）：保留在代码片段中。
3. **示例代码保留原则**：源文件中的代码片段全部保留。不要因为某个代码块"看起来不重要"就丢弃。

**第二步：全量扩充与双文档生成**
针对每个独立逻辑块，先检索 `03_Knowledge` 全库（find/grep）找出现有相关笔记。

### 复杂度分析规则（仅限算法类代码）
**必须分析复杂度的情况**：排序/搜索/图论/DP/贪心/回溯/分治/字符串匹配/数论/数据结构操作/LeetCode 风格解题代码。
**无需分析复杂度的情况**：普通工具函数（字符串 trim、文件读取封装）、配置代码、I/O 操作、框架样板代码、纯业务逻辑。
**判断标准**：核心价值在于"运行结果正确且高效"→需要；核心价值在于"完成某项业务功能"→不需要。
